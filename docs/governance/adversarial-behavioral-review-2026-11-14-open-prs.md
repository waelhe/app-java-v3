## C. Behavioral Walkthrough (أهم المسارات المتتبعة)

1. **مسار المستهلك المالي** `POST /api/v1/payments/intents/{id}/process` → ملكية → `requireChannel()` → 503 SU-001 قبل أي كتابة (لا PROCESSING/لا صف Payment/لا حدث) — #827 يغلق العيب (silent-pass سابق) لكن عبر `@Retry`+`@CircuitBreaker` غير مهيأين لتجاهل 503 (F-827-1).
2. **مسار الاسترداد فوق الحاملات**: `OrderRefundAdapter`/`PaymentRefundAdapter` → overload بـ`@Transactional(REQUIRES_NEW)` → كل محاولة `@Retry` بمعاملتها المستقلة → اختفت سمّية `UnexpectedRollbackException` — #828 سليم.
3. **القسم الحرج refund-delta**: `pg_advisory_xact_lock(hashtextextended(...))` **قبل** قراءة `findTopBy…cumulative DESC` وقبل الإدراج، داخل معاملة واحدة، عزل READ COMMITTED الافتراضي — #831 يغلق فوق-الترحيل (300+700=1000) في كلا الترتيبين.
4. **تسوية طلب PLATFORM_DELIVERY** (جديد #832): دائن البضائع 17400 + مدين عمولة 1340 + **مدين رسم توصيل 4000** ← ثم الاسترداد الكامل يعكس البضائع والعمولة فقط ← **الرصيد النهائي −4000 بدل 0** (F-832-1).
5. **محو وسائط الحساب** (جديد #833): شاهد PURGED بآلة حالة محكومة (الدرجة 1 سليمة) ← بعد الـcommit دفعة `DeleteObjects` واحدة **بلا تجزئة سقف 1000 مفتاح** (F-833-1).
6. **أنبوب أخطاء REST/GraphQL**: `MethodArgumentTypeMismatchException` → VAL-001/400 شجرياً مع `fieldErrors` (قيمة مرفوضة كحجة تنسيق لا كقالب — لا فخ MessageFormat) — #821 سليم؛ عائلة ApiProblemDetail في GraphQL بتصنيفها الذاتي بدل قناع INT-001 — #819 سليم سلوكياً (توثيق العقد ناقص F-819-1).
7. **حاجز أصل رابط البريد**: رفض null/فارغ/placeholder غير محلول/userinfo/مسار/query/منفذ خارج النطاق في كل profile قابل للنشر — #822 سليم مع شرط تشغيلي (متغير Railway قبل أول نشر).
8. **اختبارات الحراس**: E2 (استنفاد آلة الحالات النهائية)، V42 (قيد UNIQUE على PostgreSQL حقيقي بخيطين)، G4 (تقدم version ذري في نفس الجملة) — كلها تثبت القوانين المزعومة بحتمية، لا تغطية شكلية.

## D. Adversarial Findings (مرتبة بالخطورة)

### F-832-1 — P1 — سلامة محاسبية/بيانات — **يمنع دمج #832**
- الملف: `marketplace-ledger/.../LedgerPaymentEventListener.java:226-265` (فرع الاسترداد ORDER) مقابل `:126-134` (التسوية).
- المشكلة: الاسترداد الكامل لطلب PLATFORM_DELIVERY يعكس قيد البضائع (`debitFromRefund`) والعمولة (`creditFromCommissionReversal`) **ولا يعكس قيد `DELIVERY_FEE_DEBIT` الجديد**.
- المسار: تسوية ← رصيد +12060 (17400−1340−4000) ← REFUNDED ← مدين 17400 + دائن 1340 ← الرصيد النهائي **−4000** بدل الصفر.
- الشروط: أي استرداد كامل لطلب توصيل منصة (مسار أساسي لا نادر).
- النتيجة الصحيحة المتوقعة: قيد مرآة `delivery-fee-reversal-<intentId>` دائن بالرسم (نفس نمط COMMISSION_REVERSAL الموثق الذي يحمل عنوان الـPR نفسه «reversal symmetry»).
- الأثر: كل بائع مسترد لطلبه يبقى مديناً للمنصة بمبلغ الرسم الذي استُرد للمشتري — فساد رصيد تراكمي.
- الدليل: لا وجود لأي DELIVERY_FEE reversal في الملف كاملاً؛ اختبار `platformDeliveryOrderSettlementLandsTheD4Split` يثبت التسوية فقط.
- إعادة الإنتاج: تتبع حسابي مؤكد بالكود (لم يُشغَّل — بيئة المراجعة بلا JDK25/Docker).
- الثقة: عالية. التوصية: مرآة `creditFromDeliveryFeeReversal` داخل فرع الاسترداد ORDER + اختبار تكاملي يثبت العودة للصفر.

### F-832-2 — P2 — اتساق النموذج المحاسبي — #832
