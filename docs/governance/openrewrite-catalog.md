The catalog versions come from the official [latest-module list](https://docs.openrewrite.org/reference/latest-versions-of-every-openrewrite-module) aligned with recipe BOM `3.41.0`. Important Maven distinction: a project's `dependencyManagement`/imported BOM does **not** manage dependencies declared under a build plugin's `<dependencies>`. Therefore, the recipe packs are explicitly placed on the `rewrite-maven-plugin` classpath and pinned through the `openrewrite.*.version` properties, rather than merely being project dependencies. The PR workflow fails if `org.openrewrite.java.dependencies.UpgradeDependencyVersion` is absent from discovery output.

## Profiles

- `mvn -Popenrewrite org.openrewrite.maven:rewrite-maven-plugin:6.50.0:discover -Ddetail=true` resolves the baseline Java/Maven recipe set plus explicitly pinned Apache-licensed recipe packs on the plugin classpath and prints recipe availability. CI checks the discovered output for `org.openrewrite.java.dependencies.UpgradeDependencyVersion` so a successful command that silently omits an external pack cannot pass.
- The workflow first runs `mvn -DskipTests -Popenrewrite install` with its explicit Code Genome settings file, then runs `mvn -Popenrewrite org.openrewrite.maven:rewrite-maven-plugin:6.50.0:dryRunNoFork` in a separate invocation. `install`, not just `package`, ensures sibling SNAPSHOT modules such as `marketplace-shared` are present in the local Maven repository when Rewrite resolves module dependencies. The first rollout is report-only because repository-wide diffs have not yet been reviewed; the workflow uploads the diff as an artifact. Do not describe this as a blocking source-conformance gate until the baseline is clean and `failOnDryRunResults` is enabled.
- `mvn -Popenrewrite,openrewrite-third-party-free-catalog org.openrewrite.maven:rewrite-maven-plugin:6.50.0:discover -Ddetail=true` adds the Apache-licensed third-party pack while excluding the MSAL-only transitive modules observed returning HTTP 403 (`rewrite-migrate-java`, `rewrite-github-actions`, `rewrite-static-analysis`, `rewrite-joda`, `rewrite-jenkins`). Recipes requiring those exclusions are not considered covered by this free profile.
- `mvn -Popenrewrite,openrewrite-all-catalog org.openrewrite.maven:rewrite-maven-plugin:6.50.0:discover -Ddetail=true` adds the optional `rewrite-all` recipe aggregator with out-of-scope source-available language parsers excluded.
- `openrewrite-spring-source` is an **experimental diagnostic profile**, not a supported no-subscription catalog. The current probe builds the pinned source but discovery fails: upstream publishes `6.42.0-SNAPSHOT` while the profile asks for `6.41.0`, and the requested binary/transitive recipe graph returns HTTP 403. The workflow checks for `org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_5` so it cannot report success on mere command completion. Do not activate this profile for platform migrations until artifact-version alignment, all transitive access requirements, and license rights have been resolved.

## Authentication and no-subscription boundary

OpenRewrite's current [getting-started documentation](https://docs.openrewrite.org/running-recipes/getting-started) says authenticated Code Genome access is required for artifact downloads, precompiled source-available recipes are subscription-gated, and source builds are described for non-commercial use. The workflow reads `CODEGENOME_USERNAME` and `CODEGENOME_TOKEN` from GitHub Actions secrets; credentials are never committed to the POM. The default baseline profile contains Apache-licensed modules. A successful local source build is not, by itself, proof that recipe dependencies can be resolved without entitlement or that the source-available license permits commercial use.

The Spring source build is pinned to tag `v6.41.0`, commit `bb5d5af152d1f92c3cc49f8a55ddbaf2b35247fc`. The probe proved `publishToMavenLocal` can complete, but Gradle identifies the artifact as `6.42.0-SNAPSHOT`; the Maven profile currently expects `6.41.0` and the subsequent plugin resolution reaches restricted transitive artifacts. Until those are solved, Spring recipe coverage remains **unavailable/unverified** in this no-subscription baseline.

## What this does and does not claim

Implemented: BOM alignment; profile-isolated dependencies; Apache-licensed Java/Maven recipe coverage; an optional third-party catalog with the HTTP-403 transitive dependencies excluded; explicit inventory and licence boundaries; discovery/dry-run reporting; a pinned Spring source-build diagnostic that deliberately stays outside the pull-request gate.

Verified in the PR workflow: Code Genome credentialed POM/JAR downloads succeed after following signed redirects; the Apache-licensed baseline discovery and reactor-install steps pass; the source build of `rewrite-spring` succeeds in isolation. The stricter Spring recipe-discovery probe then fails because the published source artifact version does not match the configured version and Code Genome denies the requested artifact/transitive modules (HTTP 403). The default no-subscription profile does not pull `rewrite-spring` or `rewrite-third-party`; the latter has a separate limited variant excluding restricted transitive modules. Not yet proven: a clean dry-run baseline after dependency isolation; usable Spring source-build discovery; completeness of third-party composites after exclusions; or a blocking dry-run gate. The PR workflow only runs the Apache baseline; the Spring probe is schedule/manual-only and diagnostic. Recipe availability is not equivalent to automatic execution: recipes run only when explicitly activated.
