The pinned versions are checked against the effective POM produced from recipe BOM `3.41.0`, using the official [latest-module list](https://docs.openrewrite.org/reference/latest-versions-of-every-openrewrite-module) as the independent catalog reference. The latest-module list currently lists `rewrite-java-dependencies` `1.64.1` and `rewrite-jackson` `1.31.1`, but the effective POM for BOM `3.41.0` resolves those modules to `1.64.0` and `1.31.0`. This platform deliberately follows the BOM-resolved versions instead of silently overriding the BOM with stand-alone module patches; move those pins together when a later recipe BOM manages the newer patches. **Maven-specific constraint:** Maven does not use a BOM to manage dependencies declared under a build plugin's `<dependencies>`; those versions must remain explicit on the `rewrite-maven-plugin` classpath. To prevent the explicit pins from silently drifting, CI runs `maven-help-plugin:3.5.1:effective-pom` against the isolated `.ci/openrewrite-bom-audit/pom.xml`, where the same published BOM manages seven versionless direct dependencies. `scripts/openrewrite/verify-bom-alignment.py` compares those BOM-resolved versions with the root POM's plugin-dependency properties and verifies each property is actually wired to the plugin. The check fails closed on missing or mismatched coordinates, before recipe discovery. This is a verification mirror of the published BOM—not a claim that Maven applies BOM management to plugin dependencies.

## Profiles

### Baseline style and dry-run evidence

The first dry-run on the synchronized PR head `a7280fa07fd36dae7d7c6e804ce1c4703157a0b9` produced a 696-file patch (665 Java files and 31 XML files; artifact [12555549466](https://github.com/waelhe/app-java-v3/actions/runs/40082815157/artifacts/12555549466)). Its exported `SourcesFileResults` table attributed 602 Java-file results to `org.openrewrite.java.OrderImports`; the patch showed explicit imports being collapsed into wildcards (for example, several `java.util` imports becoming `java.util.*`). The repository has no active OpenRewrite style file today, and import grouping in the existing source is not a consistently enforced contract. The official `OrderImports` default follows IntelliJ settings, including a wildcard threshold of five; applying that implicit default would impose a broad style change rather than merely inventorying available recipes.

Accordingly, the report-only baseline deliberately omits `OrderImports` until a project-wide import-order convention is explicitly adopted. The root `rewrite.yml` declares the official OpenRewrite style format, sets wildcard thresholds to 999 for future formatting recipes, and explicitly configures four-space Java/XML indentation; the Maven plugin activates that style. The following dry-run showed that the `BestPractices` composite still proposes broad Maven changes, so the active baseline now excludes it as well; only `RemoveUnusedImports` remains active. Maven recipes remain discoverable in the catalog, but are not applied by the baseline until their repository-wide effects are separately reviewed. This is a measured scope reduction, not a claim that the earlier diff is clean.

The style-corrected dry-run on commit `b964dafc96a600cdad114b85e61346171f5986ef` completed successfully in [run 40083570095](https://github.com/waelhe/app-java-v3/actions/runs/40083570095); artifact `12555879561` contains 213 unique files (182 Java and 31 XML/POM), down from the original 696-file report, and adds no wildcard imports. Its exported `SourcesFileResults` table shows all 31 XML/POM files under the `BestPractices` parent; recipe results include 31 `SortDependencies` records, three `RemoveRedundantDependencyVersions`, one `ExplicitPluginVersion`, and one `OrderPomElements`. Because those 31 build-file edits were generated by the composite rather than by unused-import cleanup, the current baseline removes `BestPractices` from `activeRecipes`. This is a deliberate safety boundary based on the measured artifact.

The narrowed dry-run on commit `46b18322c3864bc8a0851228e357d642582f1b5b` completed successfully in [run 40084343907](https://github.com/waelhe/app-java-v3/actions/runs/40084343907); artifact `12556089555` contains 182 unique Java files and zero XML/POM files. At that historical measurement point the patch was intentionally left un-applied; current source changes are managed by the automated convergence workflow described above.

The source-application workflow `.github/workflows/openrewrite-apply.yml` enforces a strict zero-diff postcondition for the selected Maven modules after applying explicitly activated recipes; it retries up to five times and fails closed if those modules do not converge. The full-reactor catalog workflow `.github/workflows/openrewrite-catalog.yml` is intentionally report-only: it passes `-Dopenrewrite.dry-run.fail-on-results=false`, uploads recipe inventory and proposed diffs, and does not claim that the existing project baseline is clean. This override applies only to the catalog audit; the root property remains `true` for automatic application. The first full-project migration is an explicit `workflow_dispatch` targeting `main`; subsequent pushes use only Maven modules with Java changes. The read-only apply job exports verified patches and a review plan as an artifact. A separate write-enabled publish job consumes that artifact, creates review-sized PRs (at most 95 files), and dispatches validation. No Maven commands run in the publish job, and generated changes are never pushed directly to `main`.

## Authentication and no-subscription boundary

OpenRewrite's [getting-started guide](https://docs.openrewrite.org/running-recipes/getting-started) requires authenticated Code Genome access for current artifact downloads; the account entitlement determines which precompiled recipe artifacts can be fetched. The workflow reads `CODEGENOME_USERNAME` and `CODEGENOME_TOKEN` from GitHub Actions secrets and never commits credentials to the POM. The default baseline contains Apache-licensed recipe packs. Under the official [Moderne Source Available License guidance](https://docs.openrewrite.org/licensing/openrewrite-licensing), an organization may consume and apply source-available recipes to its own source code, but may not package those recipes in commercial products, resell them, or offer them as a paid managed service. Successful source compilation alone proves neither that every transitive artifact is accessible nor that a recipe may be redistributed.

The Spring source build is pinned to tag `v6.41.0`, commit `bb5d5af152d1f92c3cc49f8a55ddbaf2b35247fc`. The tag's Gradle build may publish a coordinate different from its tag name (the prior probe reported `6.42.0-SNAPSHOT`). The source-build workflow now captures the exact coordinate printed after `publishToMavenLocal`, fails closed if that report is absent, and passes it to Maven as `-Dopenrewrite.spring-recipes.version=...`; the former hard-coded-coordinate mismatch has been corrected. Nevertheless, this diagnostic profile runs only on schedule or manual dispatch, not in the regular pull-request catalog job, and upstream's Spring recipe project declares additional runtime recipe packs—including Moderne Source Available modules. **Usable Spring recipe coverage remains unverified** until the diagnostic job proves successful resolution of the full dependency graph and discovers the expected recipe. It is deliberately not part of the supported Apache-licensed baseline.

## What this does and does not claim

Implemented: explicit, profile-isolated plugin dependencies; a versionless audit POM imported from the same recipe BOM; an effective-POM checker that compares the versions Maven actually resolved; Apache-licensed Java/Maven baseline discovery; a bounded module-scoped automatic apply-to-fixed-point workflow; a report-only full-catalog audit; automatic dispatch and verification of repository gates after generated changes; a limited optional third-party catalog with documented transitive exclusions; explicit licensing and execution boundaries; and an opt-in Spring source-build diagnostic with measured-coordinate propagation that stays outside the default path.

Verified in the pull-request catalog run `40091888604`: Code Genome credentialed plugin POM/JAR downloads succeeded, Apache-baseline recipe discovery and the reactor `install` passed, and `dryRunNoFork` completed with `BUILD SUCCESS` and uploaded its report artifact `12559656236`. That successful dry-run **is not a zero-diff result**: the report contains `RemoveUnusedImports` changes across existing Java sources; the diff was not applied. `failOnDryRunResults=false` therefore remains intentionally report-only until that cleanup is reviewed as a separate change and the baseline can be re-measured. Do not describe this PR as a clean source-conformance gate. The BOM alignment audit added here makes the explicit plugin-version pins mechanically comparable with the published BOM. The Spring source-build job remains schedule/manual-only and its full transitive recipe discovery is not yet verified. Completeness of third-party composites after the documented exclusions is also not yet proven. Recipe availability is not equivalent to automatic execution: recipes run only when explicitly activated.
