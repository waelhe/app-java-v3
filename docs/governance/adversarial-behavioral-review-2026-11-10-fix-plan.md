## المرجعيات الرسمية الحاكمة (الإصدارات المثبتة: Java 25، Spring Boot 4.1.2، Spring
## Security 7.x، Spring for GraphQL، PostgreSQL، Hibernate عبر BOM الإقلاع)

1. **تقدم قفل التفاؤل في جملة المحو (الدفعة 1):** آلية `@Version` والقفل التفاؤلي موثقة في
   مرجع Hibernate ORM (قسم Optimistic Locking / Entity Versioning) — كل تحديث JDBC مباشر
   يترك عمود النسخة ساكناً يجتاز فحص التفاؤل عند دفع كيان محمّل قبل التحديث؛ لهذا يقدَّم
   العمود **ضمن جملة المحو نفسها**. النمط مُطبَّق ومُختبَر في المستودع نفسه سبع مرات
   (`ReviewsContentPurgeAdapter`، `BookingContentPurgeAdapter`، `DisputesContentPurgeAdapter`،
   `SearchContentPurgeAdapter`، `JobsContentPurgeAdapter` لساق cover_message،
   `KnowledgeContentPurgeAdapter` بعد #762، `ProviderProfileContentPurgeAdapter`) — وهذا
   السجل المسبق هو السند المعتمد داخل المستودع، مع سابقة #761/#762 (دمجا 2026-10-29)
   لنفس العيب حرفياً في وحدة المعرفة.
2. **حارس آخر أدمن فعّال (الدفعة 2):** نمط الحارس الثلاثي الموثق في `UserService`
   (قفل استشاري معاملاتي + عدّ عبر منظر `auth_effective_authorities` الفعّال V188 + رفض
   409) — سند PostgreSQL الرسمي: `pg_advisory_xact_lock` (قسم Advisory Locks — قفل معاملاتي
   ينفك عند الالتزام/التراجع بلا مسار فتح يُنسى)، ومنهج العدّ الموثق في تعليق الثابت نفسه
   (`LOCK_ACTIVE_ADMINS` — عدّ من السلطة الفعّالة التي يراها الدخول، لا الصفوف الميتة).
3. **عقد الخطأ الواحد عبر النقلين (الدفعة 3):** `DataFetcherExceptionResolverAdapter`
   (`resolveToSingleError`) هي نقطة الامتداد الرسمية الموثقة لـSpring for GraphQL لربط
   الاستثناءات بأخطاء GraphQL المصنفة؛ والتصنيف `ApiErrorTaxonomy` هو المفردة الواحدة
   الموثقة في `docs/api/error-contract.md` التي يبثّها REST عبر
   `GlobalExceptionHandler.handleApiProblemDetail` — عائلة
   `ApiProblemDetailException` تُحمّل تصنيفها ذاتياً (`taxonomy()` + `statusCode()`).

## تفصيل الدفعات 1–5 (المنفذة والمرفوعة على GitHub — حالة كل واحدة في جدول الترتيب أعلاه)

### الدفعة 1 — تقدم النسخة في محوّلات المحو الخمسة المتأخرة (G1+G2+G4+G5+G6)

- **النمط المعتمد (حرفياً من التوائم السبعة):** `version = version + 1` داخل جملة UPDATE
  الجدول الحي؛ مرايا `_aud` بلا عمود نسخة تبقى كما هي؛ `COALESCE(version, 0) + 1` حيث
  العمود قابل للإفراغ (`notifications.version` — قياس المخطط: nullable، بينما بقية الجداول
  `NOT NULL DEFAULT 0`).
- **مواضع التنفيذ (كلها قيست):** community (منشورات/تعليقات/فعاليات/عناصر سوق/استفتاءات
  وخياراتها عبر `UPDATE...FROM` بتأهيل `o.version` — سابقة `ProviderProfileContentPurgeAdapter`
  الموثقة لالتباس المرجع تحت `UPDATE...FROM`)، messaging (رسائل + رصائد)، notifications
  (جدول + إنشاء ملف اختبار جديد كلياً — المحوّل بلا أي اختبار اليوم)، jobs
  (title/description — توأم cover_message في نفس الملف)، catalog (provider_listings
  description/title + أسئلة/أجوبة المنتجات).
- **الاختبار:** مطابقة نمط `BookingContentPurgeAdapterTest` — تأكيد شكل الجملة
  (`contains("... , version = version + 1")`) لكل جدول حي، وتأكيد خلوّ مرايا `_aud` من أي
  نسخة، ودلالة سباق محدّدة في javadoc الاختبار (السلة المحمّلة قبل المحو تفشل دفعها).
- **دليل القبول:** اختبارات الوحدة تخضر محلياً ثم في CI (الوحدات المعنية) + مراجعة
  CodeRabbit على الـPR.

### الدفعة 2 — حارس «آخر أدمن فعّال» على باب إلغاء إسناد الدور (B1)

- **النمط المعتمد (حرفياً من `UserService`):** عند إلغاء إسناد ADMIN لحساب فعّال: القفل
  الاستشاري `LOCK_ACTIVE_ADMIN_INVARIANT` ثم عدّ `LOCK_ACTIVE_ADMINS` عبر منظر
  `auth_effective_authorities` — إن كان العدّ ≤ 1 فرفض 409 «Cannot remove the last active
  ADMIN role» (نفس رسالة الأبواب الثلاثة). الثوابت نفسها (package-private، نفس الحزمة
  `com.marketplace.identity`).
- **موضع التنفيذ:** `RoleAssignmentService.revoke` بعد حارس الدور الأساسي وقبل أي كتابة.
- **الاختبار:** حالتان في `RoleAssignmentServiceTest`: الإلغاء عندما العدّ = 1 يرمي
  ConflictException؛ الإلغاء عندما العدّ ≥ 2 يمضي (يحرس كلا الاتجاهين — لا يكسر العمليات
  المشروعة).

### الدفعة 3 — عائلة ApiProblemDetail في محلل GraphQL (D1)

- **النمط المعتمد:** فرع `instanceof ApiProblemDetailException` يقرأ التصنيف الذاتي
  (`taxonomy()` + `statusCode()`) ويشتق أقرب `ErrorType` من مفردة spring-graphql الخماسية
  الموثقة في javadoc المحلل نفسه (400/409/429→BAD_REQUEST، 404→NOT_FOUND، 401→UNAUTHORIZED،
  403→FORBIDDEN، 5xx→INTERNAL_ERROR) — extensions.errorCode/category من التصنيف الحامل
  (VAL-001/CONFLICT-001/SU-001/RL-001)، والرسالة من `getMessage()` (عقد الرسالة الموثق في
  `ApiProblemDetailException` نفسه: جملة التفصيل المجردة للوجهين).
- **موضع التنفيذ:** `GraphQlExceptionResolver.resolveToSingleError` — بعد الفرع الخاص بـ
  `ResourceNotFoundException` وقبل السقوط الداخلي.
- **الاختبار:** حالات GraphQL لكل فرد من العائلة الأربعة (BAD_REQUEST/CONFLICT/
  SERVICE_UNAVAILABLE/TOO_MANY_REQUESTS) تثبت errorCode وcategory الصحيحين — البوابة التي
  غابت حسب D1.

### الدفعة 4 — تصحيحات سجل المراجعة (ملاحظات CodeRabbit على #816)

### الدفعة 5 — E2 + D4 + W2 (فروع مستقلة، مكتملة)

## ضوابط التنفيذ (بيئة هذه الجولة)

- **المرجع النهائي لحالة كل تغيير: GitHub + CI** (أمر المالك الدائم + بروتوكول §8) —
  التجميع المحلي (JDK 25.0.5 Temurin + Maven 3.10.0 مطابق لـwrapper الـCI) يُستعمل
  **تحققَ ما قبل الدفع فقط** (تجميع + اختبارات وحدة بلا Docker)، واختبارات التكامل
  (Testcontainers) تجري في CI وحده.
- **لا دمج قبل**: خضرة الفحوص الإلزامية + مراجعة CodeRabbit الفعلية على كل PR (وتفعيلها
  بتعليق `@coderabbitai review` عند الحاجة) — وفق قواعد الحماية المثبتة.
- **تحديث السجل:** كل دفعة تُحدث صفوف نتائجها في سجل المراجعة إلى
  «fixed (commit + test)» — في نفس الـPR.
