# Records of processing activities — GDPR (EU) 2016/679 Art. 30 (ADR-0011, Plan D-15)

- **Status:** the Art. 30 documentation layer of ADR-0011 — the engineering record of WHAT the platform's processing actually is, stated from the modules' actual schemas and code paths. It is NOT the qualified legal opinion the plan's D-15 reserves to counsel (the operative-model and jurisdiction analysis remains the owner's operational gate).
- **Official basis:** GDPR Art. 30(1) — the controller's records shall include: the name and contact details of the controller; the purposes of the processing; a description of the categories of data subjects and of the categories of personal data; the categories of recipients; where applicable, transfers; envisaged time limits for erasure; a general description of the security measures (Art. 32).

## The processors/ports law

Cross-module data flows ride the **ports** (`marketplace-shared/api` contracts: the export ports, the lookup ports, the payment ports) — a module never reads another module's tables. The one external processor category is the **PSP** (payment processing) and the **push provider** (FCM HTTP v1 — the device token only). No transfer mechanism is claimed here: transfers are part of the counsel-owned operative-model analysis the plan reserves.

## The record's own maintenance law

This record states the activities from the code that performs them; the module table above is the index, not a substitute. Any new processing activity lands with its module's own ADR and updates this table in the same change — the same discipline the migration manifest and the documentation figures follow.
