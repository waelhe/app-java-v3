# مخطط المنتج والتجربة والمعمارية — منصة المجتمع المحلي

**الحالة:** أساس تصميم وتنفيذ جديد للمراجعة؛ لا يعلن أن المتطلبات كلها منفذة أو معتمدة نهائيًا.  
**خط الأساس المرجعي:** فرع main عند commit `d0a5800c527520e833c18c0abb532e1819e07ef3` بتاريخ 2026-10-11. هذا مرجع تاريخي لإعادة البناء، ويجب إعادة القياس قبل كل دفعة تنفيذية.  
**المراجع المرافقة:** [رحلات المستخدم JT-01..JT-20](community-platform-user-journeys.md)، [نظام تصميم UX والشاشات](community-platform-ux-design.md)، [مرجع المقارنة مع Nextdoor](community-platform-nextdoor-benchmark.md)، [سجل قرارات المنتج](platform-product-decisions.md)، [دليل إدارة المنتج](community-platform-product-management.md).  
**قيد الاسم:** اسم العلامة التجارية والهوية النهائية غير محسومين؛ لا يجوز افتراض «ضَيف» اسمًا معتمدًا لهذا المنتج لمجرد ظهور الاسم في محاولات Android السابقة.

## 1. القرار التصحيحي

نبني **منصة متكاملة تبدأ من نموذج المنتج وتجربة المستخدم**، وليست تطبيق Android يعرض ما توفره واجهات API، وليست مجموعة وحدات تنفذ كلٌّ منها شاشة مستقلة. الباك إند الحالي أصل مهم نعيد استخدام قدراته الصحيحة، وليس حدًا أعلى لما يمكن للمنتج تقديمه. التطبيق الأصلي هو أول سطح تجربة جوال، وليس المنتج كاملًا.

يجب أن تظل ثلاثة أنظمة متزامنة:

1. **نظام المنتج:** احتياجات الناس المحليين، ونموذج البلد/المدينة/الحي، والهوية والأدوار والثقة والعلاقات والجهات والمحتوى والخدمات والمعاملات.
2. **نظام التجربة:** التنقل والاكتشاف والتغذية والتفاعل والانتقال بين المجالات والمتابعة وحالات الفراغ والخطأ والخصوصية والتصميم المرئي.
3. **نظام التنفيذ:** الدومينات والبيانات وواجهات API والأحداث والفهرسة والإشعارات والأمن والاختبارات والتشغيل.

لا تُعامل هذه الأنظمة كمراحل متتابعة؛ كل شريحة تنفيذية يجب أن تحسّن نتيجة مستخدم قابلة للاستخدام، وأن تُكمل ما يلزم من الطبقات في حدودها.

## 2. قواعد حاكمة

- **النتيجة قبل الشاشة والوحدة:** لا تُعد المهمة منجزة لأن الشاشة ترسم أو endpoint يعيد 200.
- **الرحلة الكاملة معيار القبول:** يبدأ القياس من مقصد المستخدم وينتهي بنتيجة صادقة قابلة للمتابعة، مع حالات الرفض والفشل والتعافي.
- **مصدر حقيقة واحد لكل مجال:** لا تنشئ التغذية أو البحث أو AI نسخة موازية من السجل. كل بطاقة تحمل مرجع السجل الأصلي ونوعه وحالته ونطاقه.
- **استخدم الموجود بعد قياسه:** لا تعِد كتابة وحدة قائمة، ولا تفترض أنها مكتملة بسبب وجود API أو جدول. قِس السلوك والقيود والاختبارات أولًا.
- **أكمل الفجوة حيث تقع:** إذا كانت الرحلة تتطلب قدرة خلفية غير موجودة، فنفذها في المجال المالك مع عقد API وواجهة واختبار، لا بمحاكاة في العميل ولا بتأجيلها بصمت.
- **حدود المجال قبل مشاركة البيانات:** لكل مجال ملكية صريحة لبياناته وقواعده وانتقالاته. التكامل عبر واجهات معلنة أو أحداث حين يناسب ذلك، لا بالوصول العابر إلى مستودعات المجالات الداخلية.
- **لا microservices افتراضيًا:** يستمر Spring Modulith كـ modular monolith ما دام يلائم الحمل والفريق والتشغيل؛ الانفصال إلى خدمة مستقلة يحتاج قياسًا وحاجة تشغيلية وقرارًا منفصلًا.
- **الأمن خادمي:** إخفاء الزر ليس تفويضًا. افحص الفاعل والملكية والدور والنطاق والحالة في الخادم واختبر السماح والرفض.
- **لا نجاح وهميًا:** لا منتجات أو أسعار أو تقييمات أو حجوزات أو دفع أو إشعارات مُسلّمة أو معاملات مكتملة مصطنعة.
- **فشل قابل للاسترداد:** رسالة مفهومة، وحفظ آمن للمدخلات، ومعرفة ما حفظه النظام، ومنع التكرار عند الإعادة.
- **الخصوصية واللغة جزء من التصميم:** العربية وRTL والشاشة الصغيرة وقارئ الشاشة والتباين وإخفاء البيانات الحساسة تدخل في كل بوابة قبول.
- **AI لا يملك السلطة:** لا يمنح دورًا أو توثيقًا أو صفة رسمية، ولا يتخذ قرارًا ماليًا أو أمنيًا، ولا يرى بيانات لم تُؤهّل حتميًا.
- **الأداء بالتجربة المقيسة:** لا نضيف Kafka أو OpenSearch أو طبقات كاش أو نظام أحداث ثانٍ بسبب الحداثة؛ نضيف تقنية عندما يثبت القياس أن الحاجة تتطلبها.
- **الوثائق تضبط البناء ولا تستبدله:** كل ادعاء عن التنفيذ الحالي يثبت من الكود والاختبارات والنشر الفعلي، لا من الخطة.

## 3. تعريف المنتج

منصة مجتمعية محلية متعددة المجالات والأدوار ومقدمي الخدمات، تعمل على مستويات البلد والمدينة والحي. هدفها مساعدة الناس على فهم محيطهم والتواصل والمشاركة وحل الاحتياجات المحلية، مع وصل المجتمع بالخدمات والتجارة والمعرفة والمؤسسات.

### 3.1 مجالات المنتج

| المجال | النتيجة التي يقدمها | حدود يجب الحفاظ عليها |
|---|---|---|
| الهوية والعضوية المحلية | حساب قابل للاستخدام، ونطاق محلي واضح، وحالات ثقة قابلة للفهم | الحساب ليس الدور، والمتابعة الجغرافية ليست إثبات إقامة |
| المجتمع والتغذية | أسئلة وطلبات وتوصيات واستطلاعات ومفقودات ومنشورات محلية؛ ردود وتعليقات وتفاعلات وحل الطلب | نوع المنشور وحالة الطلب والرؤية حقائق منفصلة |
| الاستكشاف والبحث | العثور على نقاش أو فعالية أو مجموعة أو معلومة أو عمل أو سلعة أو خدمة ضمن نطاق واضح | لا توسع جغرافي صامت ولا نتيجة خاصة في البحث أو AI |
| المعرفة المحلية «تعرّف على الحي» | معلومات محلية مع مصدر ونوع وحالة وحداثة، مع اقتراح الإضافة والتصحيح والمراجعة | لا دليل سكان خاص ولا معلومات غير محسومة تظهر كحقائق رسمية |
| الأعمال ومقدمو الخدمات | ملف أصلي، الخدمات والتغطية والاتصال، توثيق وتوصيات ومراجعات منفصلة | ملكية العمل لا تعني جودة الخدمة ولا تمنح صاحب العمل حق تحرير مراجعات الآخرين |
| الرسائل الرسمية والتنبيهات | رسائل جهات مفوضة ضمن نطاق جغرافي ودورة تصحيح وسحب وانتهاء واضحة | «رسمي» و«عاجل» صلاحيتان محكومتان لا تصنيف UI؛ المقصود نشر مؤسسي، لا بث فيديو مباشر |
| المتجر والتجارة | كتالوج فعلي، تفاصيل وتوفر، سلة وطلب ودفع وتوصيل حيث تدعمها العقود | لا ادعاء شراء أو دفع أو طلب مؤكد قبل استدامة النتيجة |
| السلع المستعملة | إعلان قابل للنشر والبحث والتواصل وتحديث الحالة | لا يُخلط مع كتالوج المتجر، ولا يُعرض المباع كمتاح |
| المجالات المتخصصة | العقارات والمركبات والوظائف والخدمات المهنية والعلمية، لكل منها سماته ودورة حياته | ليست منتجات متجر عامة؛ لا تُختلق حقول أو ترخيص أو حجز |
| المجموعات والفعاليات | الاكتشاف والانضمام/الاستجابة والتحديثات والتذكيرات | الخصوصية والوقت والمنطقة الزمنية وحالة الإلغاء جزء من الرحلة |
| الرسائل والإشعارات | العودة إلى المهمة الأصلية ومتابعة الحالة عبر القنوات المصرح بها | القناة ليست مصدر حقيقة الطلب، وWebSocket ليس مساويًا لـpush |
| الثقة والسلامة والإشراف | التوثيق والبلاغات والحسم والاستئناف والتدقيق | استقلال مراجعة القرارات الحساسة وعدم كشف المبلّغ |
| لوحة التحكم | إدارة الإعدادات والمحتوى المعتمد وتفويض المشغل وسجل التغيير والتراجع | لا كود أو SQL في إعدادات العرض، ولا إعداد يغير صلاحيات المجال |
| الإعارة المدفوعة | دورة توفر وطلب وقبول ودفع وتسليم وإرجاع ونزاع إن اعتُمدت | لا تُطلق قبل حسم القرار المالي والقانوني والتزامن والتسوية |

هذا الجدول يحدد نطاق المنتج المستهدف، وليس قائمة ميزات تم التحقق من وجودها في main.

## 4. نموذج المجال والعلاقات

النموذج المقترح علاقات بين سجلات مملوكة لمجالاتها، وليس «جدولًا كونيًا» يجمع كل شيء.

- **الحساب:** هوية المستخدم والجلسة والتفضيلات. يمكن للحساب امتلاك أدوار متعددة مع سياق فاعل واضح لكل إجراء.
- **النطاق الجغرافي:** البلد ← المدينة ← الحي/النطاق المعتمد. اختيار النطاق، والمتابعة، والعضوية المثبتة، وموقع السجل حقائق منفصلة.
- **أدلة الثقة:** نوع الادعاء، مصدر الدليل، الحالة، القرار، الصلاحية، تاريخ الانتهاء أو السحب والتدقيق. لا توجد شارة عامة واحدة تثبت كل شيء.
- **السجل المنشور:** يملكه مجاله، وله نوع ومعرف ثابت وحالة نشر ورؤية ومالك ونطاق وتواريخ لازمة.
- **إسقاط الاكتشاف:** بطاقة تغذية أو نتيجة بحث أو تنبيه تشير إلى السجل الأصلي مع ما يلزم لتحديثها وإبطالها. لا تملك الحقائق التجارية ولا قواعد الصلاحية.
- **التوصية والمراجعة:** لكل منهما أصل ومؤلف وأهلية ومعنى مستقل؛ التوصية لا تثبت معاملة، والمراجعة لا تُقبل إلا وفق سياسة معلومة.
- **التواصل والطلب:** رسالة اتصال ليست طلب خدمة، وطلب الخدمة ليس حجزًا، والحجز ليس دفعًا مكتملًا. تتحدد الدلالات من المجال الذي ينفذ العملية.
- **الحدث:** يعلن انتقالًا ذا معنى من مصدره المالك، مع مستهلكين معروفين ومعالجة للتكرار والفشل. الحدث ليس بديلًا عن سجل المصدر.

## 5. تجربة الاستخدام والتصميم المرئي

### 5.1 هيكل التنقل المقترح للجوال

- **الرئيسية:** ملخص محلي ذو قيمة، نطاق واضح، أحدث/متابعة/شائع وتخصيص مفسر حيث يتوفر.
- **استكشف:** بحث واحد ومدخل إلى الأعمال والفعاليات والمجموعات والمعرفة المحلية ومجالات السوق مع فلاتر واضحة.
- **إنشاء:** نقطة بدء موحدة توجه المستخدم حسب مقصده إلى سؤال أو طلب أو توصية أو استطلاع أو مفقودات أو إعلان أو فعالية أو خدمة.
- **السوق:** اختصارات واضحة للمتجر والسلع المستعملة والعقارات والمركبات والوظائف والخدمات المتخصصة، مع فصل مساراتها.
- **التواصل:** المحادثات وطلبات التواصل التي يحق للمستخدم قراءتها. يجب أن يمكن فتح المهمة الأصلية من الرسالة.
- الملف الشخصي والمركز الشخصي مدخل ثابت للطلبات والإعلانات والمتابعات والمجموعات والفعاليات والتوثيق والخصوصية والإعدادات. يظهر مدخل الإشعارات دائمًا بوضوح، والتنبيه الرسمي العاجل المؤهل يظهر وفق سياسة مستقلة.

هذه بنية بداية للاختبار وليست قفلًا على أي ميزة كعلامة تبويب مستقلة. في أحجام النوافذ الكبيرة تتكيف البنية بدل تكبير شاشة الهاتف حرفيًا.

تفاصيل الرموز والمكونات ومعرّفات CMP والشاشات وحالاتها موثقة في ملف [تصميم UX ونظام التصميم](community-platform-ux-design.md). يجب أن يكون هذا الملف متوافقًا مع قرار Android الأصلي ومع أحدث نسخة من رحلات JT-01..JT-20، لا مع مسودة Flutter القديمة.

### 5.2 نظام التصميم

يُبنى Design System عربي أولًا باستخدام Material 3 وMaterial 3 Expressive المتاحين رسميًا لـJetpack Compose، مع هوية مخصصة للمنتج لا تقلد Nextdoor حرفيًا:

- Design tokens مركزية للألوان الدلالية، والطباعة، والمسافات، والزوايا، والحدود والارتفاعات والحركة؛ لا قيم متكررة مشتتة في الشاشات.
- فصل ألوان العلامة عن ألوان الحالة. الدلالات مثل خطأ/نجاح/تنبيه ليست مجرد تزيين، والرسالة الرسمية لا تعتمد على اللون وحده.
- خطوط تدعم العربية جيدًا، وتدرج بصري واضح للعناوين والنصوص الثانوية والبيانات الوصفية؛ دعم الأرقام والعملات والتواريخ المحلية والنص المختلط العربي/اللاتيني.
- بطاقات موحدة لغرضها لا لقالب واحد لكل المجالات: بطاقة سؤال تعرض الحاجة والحي والوقت والردود؛ بطاقة عمل تعرض نطاق الخدمة وأنواع التوثيق الفعلية؛ بطاقة منتج تعرض السعر والتوفر؛ بطاقة معرفة محلية تعرض المصدر والحداثة.
- حالات موحدة للتحميل والفراغ والخطأ وانقطاع الشبكة وعدم الأهلية والانتهاء والسحب والتراجع، مع خطوة تالية واحدة ذات معنى.
- عناصر تفاعلية واضحة، ومساحات تنفس كافية، وتسلسل هرمي قابل للمسح، ووسائط ذات قص ونسب ثابتة، وحركة مختصرة غير مزعجة. لا تملأ الرئيسية بعشرات الأقسام أو البطاقات المتنافسة.
- حالات داكنة وفاتحة، ودعم ألوان النظام حين ينسجم مع العلامة، مع ضبط التباين والنصوص لاختبار الوصول.
- لا لون نهائي أو شعار أو اسم علامة قبل اعتماد قرار الهوية. تُعتمد الاتجاهات البصرية بعد نموذج تفاعلي واختبار استعمال، لا بناءً على مظهر لقطة شاشة فقط.

### 5.3 تفاصيل رئيسية

- في أعلى الرئيسية يظهر النطاق المحلي النشط ومبدّل نطاق مقصود؛ لا يخلط بين الحي الذي يتابعه الشخص والعضوية التي ثبتت.
- توضح بطاقة كل عنصر المصدر والوقت والنطاق والصفة التجارية أو الرسمية عند اللزوم.
- البحث يصرّح بالفئة والنطاق الفعال، ويطلب توضيحًا عند الغموض بدل توسيع النتائج بصمت.
- الإجراء الأساسي الوحيد يبرز بصريًا في كل شاشة؛ الإجراءات الثانوية تبقى متاحة دون منافسة.
- إنشاء المحتوى يعرض الصفة التي سينشر بها المستخدم والجمهور والنطاق قبل التأكيد.
- الملف التجاري يظهر التوثيق والتوصية والمراجعة والإعلان المدفوع كأدلة منفصلة.
- أي واجهة دفع أو حجز تعرض الحالة التالية الصحيحة والعواقب المالية قبل التأكيد، ولا تكتفي برسالة نجاح شكلية.

### 5.4 الوصول والشاشات

معيار التصميم يشمل TalkBack وCompose semantics، والتنقل بلوحة المفاتيح، وحجم نص متغير، وتباينًا كافيًا، وأهداف لمس مناسبة، وعدم الاعتماد على اللون وحده. تختبر الواجهة على نطاق 320–390dp، وأجهزة لوحية وقابلة للطي وأوضاع نافذة متعددة؛ لا يسمح بتمرير أفقي للصفحة بسبب RTL أو نص عربي طويل.

## 6. معمارية العميل الأصلي Android

**الاتجاه:** Kotlin + Jetpack Compose، تطبيق أصلي وليس WebView. تبقى كل نسخة مكتبة وتكوين Android Gradle Plugin وSDK ضمن الإصدارات المستقرة المثبتة في Version Catalog والموثقة وقت التنفيذ؛ لا تُنسخ أرقام إصدارات من مقالات غير رسمية ولا تدخل مكتبات alpha إلى مسار الإنتاج دون قرار.

### 6.1 طبقات العميل

- **UI / feature:** Composables تعرض الحالة وتطلق intents، ولا تنفذ HTTP أو قواعد عمل مباشرة.
- **ViewModel / state holders:** حالة شاشة صريحة، وعمليات مستخدم، وتدفق أحادي الاتجاه UDF باستخدام StateFlow/Flow وجمع واعٍ لدورة الحياة.
- **domain/use cases:** تضاف حيث يوجد سلوك معاد الاستخدام أو تنسيق متعدد المصادر، لا طبقة شكلية لكل استدعاء.
- **data/repositories:** مصدر واحد لحقائق التطبيق، ومهايئات REST وقاعدة بيانات محلية/إعدادات عند الحاجة.
- **core:** تصميم، شبكة، نماذج مشتركة، مصادقة، تخزين وإعدادات، وسائط، مراقبة؛ تُفصل Gradle modules عندما تحمي حدًا معماريًا أو تقلل الاقتران، وليس لمجرد كثرة المجلدات.

### 6.2 قواعد التكامل

- عقود REST/OpenAPI الفعلية هي مرجع العميل. يضاف توليد عميل نوعي آلي عندما يلائم خطوط العقود، ولا تُنسخ DTOs يدويًا بصورة تنحرف بصمت.
- كل كتابة تتبع عقد idempotency ملائم للعملية، وتعرض نجاحًا بعد تأكيد الخادم فقط. عند انقطاع الشبكة لا يوحى بأن الأمر حُفظ.
- OAuth Authorization Code + PKCE عبر متصفح النظام وعميل عام؛ لا أسرار في APK. تطابق redirect URI مع الإعداد المنشور، ويمر تسجيل الخروج عبر عقد هوية واضح.
- حفظ المسودات المحلية غير الحساسة ممكن؛ التخزين المؤقت للقراءة لا يحوّل بيانات قديمة إلى حقيقة مؤكدة. أي كتابة مؤجلة تتطلب سياسة تزامن وتعارض واضحة.
- رفع الوسائط يتبع عقد الخادم والتخزين؛ لا يُرسل Bearer token إلى مضيف تخزين خارجي عند استعمال رابط موقّع.
- روابط deep links تتحقق من الوجهة والصلاحية وتعيد المستخدم للمسار الأصلي بعد الدخول، ولا تكشف محتوى خاصًا.
- push والرسائل والبحث تعمل عبر الخدمات المالكة الخلفية. لا تنفذ طبقة العميل قواعد صلاحية بديلة عن الخادم.

### 6.3 الجودة والأداء

Unit tests للـViewModels والتدفقات والمستودعات، واختبارات عقد الشبكة، وCompose UI/navigation tests، واختبارات رحلات على جهاز/محاكي في CI، ثم اختبارات أداء حرجة باستخدام Macrobenchmark وBaseline Profiles حيث تتوفر بيئة القياس. نقيس startup والتمرير والذاكرة وحجم الحزمة بدل الادعاء بأنها سريعة.

## 7. معمارية الباك إند والمنصة

### 7.1 خط الأساس

وفق README الحالي عند اللقطة المرجعية، المستودع نظام Spring Boot 4.1.1 / Java 25 / Spring Modulith 2.1.1، مع PostgreSQL 18 وPostGIS وRedis 8 وFlyway وطبقات REST وGraphQL، وعميل/بوابة edge قائمة. هذه حقائق أولية مصدرها المستودع؛ تُعاد مطابقتها قبل التنفيذ. لا نستنتج أن كل المجال المقابل مكتمل لمجرد وجود وحدته.

### 7.2 الاتجاه المعماري

- الاستمرار في **modular monolith** بدل الانتقال إلى microservices دون حاجة مثبتة.
- المجال المالك يملك نموذجه واستدامته وحالات انتقاله. حدود الوحدات والفئات العامة تُتحقق بأدوات Spring Modulith في CI.
- التفاعل المباشر بين وحدتين يسمح به عبر واجهة عامة موثقة عندما يلزم استعلام أو قرار متزامن؛ يستخدم الحدث للمستمعين المستقلين بعد انتقال أعمال مستدام. لا يسمح للمنسق بامتلاك قواعد رؤية مجال آخر.
- تعتمد معالجة أحداث Modulith على سجل نشر الأحداث/المستمعين وإعادة المعالجة والتطهير وفق الوثائق الرسمية؛ لا ننشئ event bus أو worker آخر قبل إثبات أن المسار الحالي غير كافٍ.
- تبقى Flyway المصدر الرسمي لتطور المخطط، ولا تعدل ترحيلات سبق تطبيقها؛ أي تغيير يأتي بترحيلة تصاعدية جديدة واختبارها على قاعدة حقيقية.
- يظل PostgreSQL/PostGIS خط أساس أوليًا للجغرافيا والبيانات والبحث النصي. يقارن OpenSearch فقط عند توفر corpus عربي موسوم وقياسات للدقة والزمن والتكلفة التشغيلية.
- يمر البحث وAI عبر نفس أهلية السجلات؛ الاسترجاع القانوني يسبق التوليد، ومصدر الإجابة ظاهر. فشل AI يجب أن يترك البحث الحتمي يعمل.
- لا يُدّعى exactly-once عبر الشبكة. تُحدد كل عملية ذات أثر خارجي بالمفتاح والحالة والتكرار والتعافي الممكن.
- واجهة API إصدارية موثقة بعقود متوافقة، واستجابات أخطاء ثابتة، وحدود معدل، وتفويض واختبارات صلاحيات، ومقاييس تشغيل لا تسجل أسرارًا.

### 7.3 الأحداث والبحث والإشعارات

التغذية والفهرس والبحث والإشعارات مستهلكون لإشارات مصدرية، لا مصادر الحقيقة. لكل حدث: منتج مالك، مخطط، مستهلك، سياسة تكرار، فشل وإعادة تسليم، ومقياس واضح. تغييرات الحالة مثل النشر والتحديث والسحب والانتهاء والتوثيق وتوفر الخدمة تعكس على الأسطح المرتبطة؛ لا يبقى السجل القديم متاحًا لمجرد أنه مخزن في cache.

تُرسل الإشعارات بسبب أحداث أعمال مستحقة، مع سياسة للمستلم والقناة والتفضيلات والإلحاح. حفظ سجل الإشعار لا يعني أن push سُلّم. ويجب أن يعود المستخدم إلى السجل الأصلي بأهلية تُفحص من جديد.

### 7.4 الأمن والثقة

الهوية، والعضوية المحلية، وملكية العمل، والأهلية المهنية، وتفويض الجهة، وحق الإشراف أدلة مستقلة. القرار الخادمي يعتمد الدور والملكية والنطاق والحالة معًا. الطلبات الحساسة مدققة، والوثائق الخاصة لا تظهر في البحث أو السجلات أو سياق AI. تُختبر حالات الرفض إيجابيًا وسلبيًا ولا يكفي إخفاء عناصر الواجهة.

## 8. عقد الربط بين المجالات

تعمل المجالات كسجل أصلي وواجهات مترابطة لا كصفحات مستقلة:

- المجتمع يمكنه الإشارة إلى سجل نشاط أو خدمة أصلي دون نسخ اسم النشاط أو الهاتف أو التقييم أو السعر داخله.
- توصية محلية يمكن أن تقود إلى ملف العمل الأصلي ثم إلى خدمة منشورة وقناة تواصل مدعومة، مع حفظ سياق الإحالة دون منح صلاحية.
- إيقاف العمل أو سحب التوصية أو انتهاء المنتج ينعكس في البحث والتغذية والإشعارات، ويعاد فحص المصدر عند فتح التفاصيل.
- رسائل المؤسسة تستخدم سجل الجهة والتفويض والنطاق ودورة السحب؛ لا تنتج قناة رسمية موازية.
- المنتجات وخدمات المجتمع لا تظهر في واجهات التجارة من خلال نسخ مكررة. تملك كل معاملة المجال المحدد الذي ينفذها فعلًا.
- إتمام رسالة أو حجز أو طلب أو دفع لا يثبت إلا من مصدر الحالة المالك لذلك العمل.

## 9. خطة التنفيذ الجديدة: شرائح منتج من الطرف إلى الطرف

هذه خريطة ترتيب مبدئي؛ الأولوية الدقيقة تتأكد بعد قياس main واختبارات النشر. ليست قائمة وحدات يجب إنهاؤها بالتتابع قبل ربطها.

### S0 — استعادة الحقيقة وإزالة الالتباس

قياس commit الإنتاجية وmain، حالة PRs والفروع والتبعيات والترحيلات ومخططات API والاختبارات. توثيق ما هو موجود فعلًا وما هو مطلوب وما هو عالق. إغلاق محاولات العميل المتكررة وخطط التنفيذ المتعارضة بعد حفظ المعارف الصالحة في أساس واحد. لا تغيير مخطط أو كود إنتاجي لمجرد تنظيف التاريخ.

**بوابة النجاح:** جرد قابل للتحقق، ومرجع واحد للمنتج والتجربة، ومصفوفة واضحة بين الرحلات والقدرات الحالية والفجوات والاعتماديات.

### S1 — الانضمام إلى مجتمع محلي وأول قيمة

رحلة متكاملة تبدأ بالزيارة والدخول واختيار النطاق وتوضيح معنى التحقق، ثم الوصول إلى الرئيسية ذات المحتوى المناسب أو حالة فراغ مفيدة، وإدارة المتابعات والخصوصية وحالة الحساب. تشمل API وقواعد الأهلية وعقد الجوال والاختبارات.

### S2 — حاجة مجتمعية حتى جواب/حل

ينشئ المستخدم سؤالًا أو طلبًا، يحدد نوعه ونطاقه ورؤيته، ينشره مرة واحدة، يتلقى الردود والإشعارات، يتابع الحالة، ويغلق الطلب أو يعلن الحل حيث يدعم النوع ذلك. يشمل إدارة المحتوى والبلاغات اللازمة لمنع إطلاق مجتمع بلا مسار سلامة.

### S3 — استكشاف وبحث موثوقان

بحث عربي ونطاق صريح وفلاتر منضبطة ونتائج متعددة المجالات مع مصادرها وحالاتها. ترتبط النتائج بتفاصيل حقيقية. قياس جودة corpus العربي والخصوصية والفشل الآمن قبل أي توسع إلى محرك إضافي أو ترتيب متعلم.

### S4 — من التوصية إلى عمل وخدمة وتواصل

ملف عمل أصلي، وأنواع التوثيق، والتوصيات والمراجعات، ونطاق التغطية، والخدمة الفعلية، والاتصال/الرسالة/الطلب المتاح، والمتابعة والعودة إلى السؤال. تمنع الرحلة ازدواج السجلات وادعاءات المعاملة غير المثبتة.

### S5 — المعرفة المحلية القابلة للتحديث

تصفح معلومة بمصدرها وحداثتها، اقتراح إضافة أو تصحيح، مراجعة وصلاحية، نشر التغيير، وتحديث الإسقاطات. توجد سياسة مصدر ومراجعة مناسبة لتأثير كل فئة ومقاييس لاكتشاف المعلومات القديمة.

### S6 — المؤسسات والرسائل الرسمية

إثبات الجهة والتفويض والنطاق، إنشاء ومراجعة ونشر وتصحيح وسحب وانتهاء الرسالة، ثم تسليم التنبيهات المؤهلة للمستخدمين المستهدفين. لا يُفتح مسار «عاجل» حتى تثبت مصفوفة السلطة والاختبارات.

### S7 — المتجر والمعاملات

كتالوج وتوفر وسعر صحيح وصور، تفاصيل، سلة، طلب، دفع، توصيل، إلغاء/استرداد وحالات استثنائية وفق دورة تجارية مكتملة. لا يعلن عن شراء ناجح قبل الاستدامة والتأكيد الصحيح من مزود الدفع أو النظام المالك.

### S8 — العموديات الأخرى

العقارات والمركبات والوظائف والخدمات المهنية/العلمية تستخدم البنية المشتركة للهوية والجغرافيا والبحث والتواصل، مع نماذج ودورات مجال منفصلة. لا تؤدي إعادة استخدام الواجهة إلى محو الاختلافات القانونية والوظيفية.

### S9 — المجموعات والفعاليات والتواصل المستمر

اكتشاف المجموعة والانضمام والعضوية والخصوصية؛ اكتشاف فعالية والتسجيل أو الاهتمام والتذكير والتعديل والإلغاء؛ محادثات وصندوق إشعارات وحظر وكتم وبلاغات حسب الدعم المعلن.

### S10 — إدارة المنصة والثقة والسلامة والتوسع

لوحة تحكم ذات صلاحيات ومخططات إعدادات ونسخ وتراجع وتدقيق، وإدارة التوثيق والبلاغات والاستئناف، وتوافق العملاء ومراقبة جودة الاكتشاف. تنفذ القدرات اللازمة لهذه الرحلات قبل S10 إذا كانت شرطًا للسلامة أو تشغيل أي شريحة؛ أرقام الشرائح ليست سببًا لتأجيل ضرورة وظيفية.

### S11 — صلابة الإنتاج والتحسين

رحلات E2E كاملة على بيئة واقعية مع حالات السحب والتعارض والتكرار وتعطل مزود وبيانات خاصة؛ قياس الوصولية وRTL والأداء والتعافي والتكلفة. تحسين الترتيب أو إضافة بنية توزيع جديدة لا يبدأ قبل خط أساس وتجربة قابلة للمقارنة.

## 10. معيار إنجاز كل شريحة / PR

كل PR يجب أن يعلن:

1. ما نتيجة المستخدم التي ينجزها ومعرفات JT وAC ذات الصلة.
2. ما قيس في main والبيئة الفعلية، وما كان موجودًا وما تغير.
3. المجالات والواجهات والبيانات والعقود والأحداث المتأثرة ومصدر ملكيتها.
4. المسار السعيد، والحالات المرفوضة، والملكية والنطاق، والفشل، والاسترجاع والتكرار بحسب طبيعة الرحلة.
5. اختبارات الوحدات والتكامل والعقد والعميل والرحلة الحقيقية، مع نتيجة كل فحص على SHA معروف.
6. التحقق المرئي من RTL والشاشة الصغيرة والوصولية وحالات التحميل/الفراغ/الخطأ حيث يتأثر العميل.
7. المراقبة وسلوك التشغيل والعودة للإصدار السابق إذا كان التغيير عالي الأثر.
8. فجوات معلومة وقرار المالك المطلوب؛ لا TODO مخفي ولا ادعاء اكتمال غير مثبت.

لا يلزم أن يحتوي كل PR على عشرات الرحلات؛ يلزم أن تكون الشريحة صغيرة بما يكفي للمراجعة، وكاملة بما يكفي لإثبات نتيجة حقيقية. لا نجزئها إلى PR للـAPI وآخر للشاشة وثالث لربط الأحداث إذا ظلت القدرة مكسورة بين تلك PRs، إلا عندما تفرض تبعية مستقلة ذلك ويظل وصف الاكتمال صريحًا.

## 11. بوابات الإصدار

لا تُطلق الرحلة إذا فشل واحد من التالي بما يؤثر فيها:

- صلاحية أو ملكية أو نطاق جغرافي غير مفحوص خادميًا.
- محتوى خاص يظهر في البحث/AI/الإشعار أو استمرار نسخة مسحوبة كمحتوى نشط.
- واجهة نجاح دون تأكيد السجل المالك.
- تكرار كتابة أو إشعار أو عملية مالية عند retry.
- عقد API والعميل غير متوافقين أو أخطاء غير قابلة للفهم.
- غياب اختبار حقيقي لقاعدة البيانات والترحيلات ذات الصلة.
- RTL أو الوصولية أو أحجام الشاشة تسبب عائقًا جوهريًا.
- فشل بيئي يُسجل نجاحًا أو بوابة لا يمكن تشغيلها دون تصريح.
- عدم وجود مسار لاسترداد المستخدم أو التعامل مع الحالة النهائية.
- عدم وجود دليل مقيس على commit الذي سيُطلق.

اخضرار CI شرط لازم وليس تفويضًا للدمج. لا دمج أو إطلاق دون قرار المالك الصريح.

- لا إنشاء عميل Android رابع ولا PR بديل قبل مراجعة هذا الأساس وتحديد شريحة البداية.

يُسجل كل تنظيف برقم PR والحالة قبل/بعد والسبب والمرجع الذي يحفظ المعرفة المفيدة. لا تغييرات صامتة. تُعاد قراءة حالة GitHub قبل كل إجراء، لأن حالة الفروع وCI تتغير.

قبل اعتماد تفاصيل UI النهائية أو بدء موجة برمجية واسعة:

- إعادة قياس main وطلبات الدمج الحالية والاختبارات والترحيلات وخدمات النشر.
- مراجعة مواصفة الرحلات الـ17 مقابل المجالات الحالية وتحديد فجوة كل AC مع دليل.
- اعتماد اتجاه الهوية المرئية والتنقل الأولي عبر نموذج قابل للتجربة، مع بقاء اسم العلامة غير محسوم.
- تثبيت إصدارات Android المستقرة والمكتبات بعد التحقق من الوثائق الرسمية وبيئة CI.
- اختيار أول شريحة E2E وكتابة معايير قبولها قبل أي شاشة أو endpoint جديد.
- حفظ حالة كل قرار وحدوده وصاحبه؛ لا يعلن أي جزء مكتملًا دون قياس واضح.

**قاعدة النهاية:** لا نبني وحدات متجاورة على أمل أن تتحول لاحقًا إلى منصة. نبني رحلة حقيقية، ثم نوسّعها عبر المجالات مع الحفاظ على نموذج المنتج والتجربة والمعمارية نفسها.
