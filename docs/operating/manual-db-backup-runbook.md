# Runbook — النسخ الاحتياطي الآلي لقاعدة الإنتاج + إجراء الاسترجاع

> **القناة الحاكمة الآن (2026-10-14):** سير العمل الآلي `.github/workflows/db-backup.yml` — تنفيذ النسخة صار **آلياً بالكامل** (جدولة يومية + نداء من قناة النشر قبل كل حدث نشر) وفق تعليم المالك الحاكم: «أي تدخل يدوي بدل الإدارة التلقائية قم بإزالتها بدون استثناء وفعل الإدارة التلقائية». هذا الملف لم يعد إجراء تنفيذ يدوياً — بقي منه **إجراء الاسترجاع وحده** (قرار بشري وقت الحادث بحكم التصميم: أي نسخة، أي لحظة، بأي نافذة فقد مقبولة — لا جدولة تكتب إلى قاعدة الإنتاج أبداً).

---

## 1. القناة الآلية — ماذا تفعل بلا أي تدخل

- **الجدولة اليومية:** 01:13 UTC يومياً (دقائق مُزاحة عن رأس الساعة — التوجيه الرسمي نفسه المتبع في fork-sync)، تعمل من آخر كوميت على الفرع الافتراضي (عقد `schedule` الموثق).
- **نداء قناة النشر:** السير قابل للاستدعاء (`workflow_call`) — قناة النشر تأخذ لقطة قبل كل نشر (أرضية الأمان قبل أي ترحيلة Flyway جديدة).
- **المصارف الذاتية:** يكتشف خدمة postgres ويقرأ اتصالها الحي (`DATABASE_PUBLIC_URL`) عبر قناة GraphQL نفسها التي تثق بها قناة النشر (`RAILWAY_TOKEN` الموجود أصلاً) — **صفر أسرار جديدة، صفر تهيئة يدوية**.
- **الصيغة والقناة:** `pg_dump -Fc` (الصيغة custom المضغوطة، القابلة للاسترجاع المتوازي بـ`pg_restore -j`) → أثر Actions موثق (`actions/upload-artifact` — قناة التخزين الرسمية) باحتفاظ 30 يوماً.
- **قناة كلمة المرور:** ملف libpq المحمي (`~/.pgpass` بصلاحية 0600 على مشغّل سير مؤقت — «The Password File» في وثائق PostgreSQL) — لا سطر أوامر، لا `ps`، لا `GITHUB_ENV`.
- **العميل الموافق:** `postgresql-client-18` من مستودع pgdg الرسمي (apt.postgresql.org) — عقد pg_dump الموثق: «العميل بنفس إصدار الخادم أو أحدث».

## 2. كيف تسترجع (الإجراء البشري الوحيد — وقت الحادث فقط)

1. **نزّل الأثر** من صفحة تشغيل سير «Database Backup» المعني (أو عبر واجهة Actions) — الملف: `production-<YYYYMMDD-HHMMSS>.dump`.
2. **تحقق من سلامة الأرشيف** بحالة خروج (`--list` = «List the table of contents of the archive» — المرجع الرسمي):
   ```bash
   pg_restore --list production-<...>.dump > /dev/null && echo "الأرشيف سليم البنية"
   ```
3. **استرجع إلى هدف صريح** — على Railway: قاعدة/خدمة **جديدة** أولاً ثم بدّل (نمط نافذة الاسترجاع الموثق في نقل postgres-17→18) — لا استرجاع فوق الحية إلا بقرار صريح:
   ```bash
   pg_restore --clean --if-exists -j 4 --no-acl --no-owner --dbname="$TARGET" production-<...>.dump
   ```
   - `--no-acl --no-owner`: امتيازات/ملكية المرتفع ملك Railway — إعادة إنشائها خارج المنصة تعطل الترميم.
4. **ثم `ANALYZE` ثم تحقق الأعداد** (عدد الجداول والصفوف المفصلية مقابل ما قبل الحدث — نفس بروتوكول تحقق النقل 57/57).

## 3. عقد صادق — ما تفعله القناة وما لا تفعله

- **الجدولة موجودة والإنذار موجود:** فشل النسخة اليومية = فشل run مرئي في Actions (لا صمت تشغيلي). RPO = عمر أحدث لقطة (يوم واحد في الحالة اليومية؛ أقصر عند لقطات ما قبل النشر).
- **ليس PITR:** الاسترجاع يعود إلى **لحظة النسخ** حصراً، لا «أي لحظة في نافذة 4 أسابيع» — ترقية PITR/pgBackRest بند مدفوع يُفتح بقرار المستخدم حصراً.
- **لا يغطي Redis:** جلسات ومخبآت قابلة لإعادة البناء بلا قيمة استرجاعية (لا تحمل بيانات أعمال أصيلة).
- **نافذة 30 يوماً:** الأقدم تتلاشى مع انتهاء احتفاظ الأثر — احتفاظ أطول (حتى 90 يوماً) أو تصدير خارجي بند قرار، لا افتراض.
