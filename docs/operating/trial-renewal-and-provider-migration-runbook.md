# Runbook — تجديد الفترة التجريبية وترحيل حساب Railway والانتقال لمزوّد آخر (خطة التكرار عند انتهاء التجربة)

> **البند الحاكم:** أمر المستخدم «وثق كل عملية تشغيل على المشروع في حالة الحاجة لتكرارها الشهر القادم بعد انتهاء الفترة التجريبية وتجديدها او الانتقال لمزود اخر» (2026-09-20). القياس الكامل لحظة-بلحظة في SYSTEM.md §15 (إدخالا 2026-09-19 و2026-09-20) و`docs/railway-deployment-reference.md` §0.7 — هذا الـrunbook يحوّل ذلك السجل إلى **خطوات قابلة للتنفيذ الحرفي** عند أي تكرار.
>
> **التصنيف:** وثيقة عمليات حصراً — صفر كود، صفر ترحيلات، صفر متغيرات جديدة (`.dockerignore` يستثني `*.md` من سياق البناء فشجرة التشغيل لا تُمس). **سياسة الأسرار سارية على كل خطوة أدناه:** أسماء المتغيرات تُوثَّق هنا؛ **قيمها لا تدخل المستودع قط** — قناتها الرسمية قناة API الحية الموثقة في §7.

## 1. الحقيقة المعمارية التي تجعل أي تكرار رخيصاً — حاوية واحدة + 45 متغيراً

القياس المقيس على حساب v3 (2026-09-19/20): **كل تبعيات التطبيق خارج Railway إلا حاوية التطبيق نفسها.** هذا ليس صدفة بل نتيجة قرارات موثقة سابقة (انتقال قاعدة البيانات إلى Neon 2026-09-18، وRedis إلى Upstash، والبريد عبر Resend، والوسائط عبر Backblaze B2) — فالترحيل بين الحسابات أو المزوّدين **ليس ترحيل بيانات** بل إعادة تشغيل حاوية واحدة بمجموعة متغيرات معروفة:

| التبعية | المضيف الحالي (مقيس 2026-09-19) | علاقتها بـ Railway |
|---|---|---|
| كود التطبيق | `waelhe/app-java-v3@main` على GitHub | خارجية — قناة GitHub App للسحب والبناء |
| قاعدة البيانات (PostgreSQL 18.6) | **Neon** — القناة المباشرة `ep-weathered-pond-b2vgv0jc.c-6.eu-central-1.aws.neon.tech/neondb` بـ `channel_binding=require` | **خارجية بالكامل** — لا تُمس عند أي ترحيل؛ سجل Flyway الحي عليها 67 مدخلاً (الفهرس V66) |
| Redis | **Upstash** (`REDIS_HOST` مقيس) | خارجية |
| البريد | **Resend** (`MAIL_HOST=smtp.resend.com`) | خارجية |
| الوسائط (S3-compatible) | **Backblaze B2** (`MEDIA_S3_ENDPOINT` مقيس، bucket ‏`marketplace-dayf`) | خارجية |
| حاوية التطبيق | خدمة واحدة `app-java-v3` على Railway (بناء Dockerfile الرباعي + AOT) | **هذا كل ما يملكه Railway** — وهو الموضوع الوحيد لهذا الـrunbook |

**النتيجة العملية لكل سيناريو:** تجديد الحساب = دفعة بلا خطوات تقنية (§4)؛ حساب جديد = إعادة تشغيل الحاوية + نقل 45 متغيراً + إعادة ربط معرف cache-mount (§5)؛ مزوّد آخر = نفس الصورة والمتغيرات على منصة جديدة (§6). قاعدة البيانات وسجلها ومحتواها لا يتحركان في أي من الثلاثة.

## 4. السيناريو أ — التجديد على نفس الحساب v3 (الأسهل: صفر خطوات تقنية)

عند انتهاء الفترة التجريبية **على الحساب نفسه** (`c8ba2537`) وترقيتها لخطة مدفوعة من لوحة Railway (Settings → Usage/Billing → Upgrade):

- **لا شيء من هذا الـrunbook يُنفَّذ.** الكود والمتغيرات والنطاق وقاعدة البيانات كلها باقية كما هي — الدفع يرفع حدود الاستهلاك فقط.
- المتغيرات الـ45 والإعدادات والـIaC سجلات معلنة مطابقة للحالة الحية — لا إعادة ضبط.
- **التحقق الوحيد المطلوب بعد الترقية:** جولة watchdog التالية خضراء (تلقائي) + فحص دخان يدوي سريع (§8) إن أردت اليقين الفوري.
- ما يستحق النظر مع الخطة المدفوعة (قرارات كلفة بيد المستخدم، موثقة في `docs/railway-deployment-reference.md` §0.5-ديون): تفعيل PITR لقاعدة البيانات إن انتقلت لاحقاً لاستضافة داخلية (ليست على Railway الآن — القاعدة على Neon)، واختيار مزوّد `OTEL_*` لتفعيل الرصد (النقاط المنقولة حالياً لا تصدّر — `localhost:4318`).

## 5. السيناريو ب — حساب Railway تجريبي جديد (تكرار الهجرة الشهر القادم)

> **متى:** قررت فتح حساب تجريبي جديد بدل تجديد الحساب الحالي. الزمن التقديري بالخبرة المقيسة: **~60–90 دقيقة** (منها ~25 دقيقة بناء أول بارد + ~20 دقيقة CI على الـPR).
>
> القاعدة الحاكمة لكل خطوة: **قِس قبل أن تنفّذ** — كل أمر أدناه له تحقق عكسي لأن الأرقام التعريفية (معرف الخدمة، النطاق) ستتغير حتماً بين الحسابات.

### الخطوة 0 — المتطلبات المسبقة
1. حساب Railway جديد + مشروع جديد باسم `app-java-v3` من لوحة الحساب.
2. **توكن project-scoped** من لوحة المشروع (Settings → Tokens) — احتفظ به محلياً في ملف محمي خارج المستودع (قناة الأسرار §7).
3. توكن GitHub بصلاحيات repo/contents:read (المستودع عام لكن الدفع والـworkflow يحتاجان التوكن — نفس القناة المستخدمة تاريخياً).
4. Docker محلي أو اكتفِ بـ CI كبوابة (نمط الجلسات السابقة).

### الخطوة 1 — إنشاء الخدمة وربط المستودع
من لوحة المشروع الجديد: New Service → **GitHub Repo** → `waelhe/app-java-v3` → فرع `main`. هذا يركّب قناة GitHub App مباشرة بلا fork (نفس حالة v3). **لا تنشر الآن** — البناء سيفشل فوراً بفخ الخطوة 3 (هذا متوقع ومقيس: الرفض يحدث قبل جدولة البناء).

### الخطوة 2 — قياس الأرقام التعريفية الجديدة
```python
# نمط discovery المقيس: GraphQL v2 على backboard.railway.app/graphql/v2
# بالتوكن الجديد — استخرج: projectId, environmentId(production), serviceId(app-java-v3)
query { projects { edges { node { id name environments { edges { node { id name serviceInstances { edges { node { id serviceName } } } } } } } } } }
```
**سجّل `serviceId` الجديد فوراً** — هو مفتاح الخطوة التالية (فخ البناء الوحيد).

### الخطوة 3 — إعادة ربط معرف الـcache-mount (فخ البناء الإجباري)
سطر Dockerfile (17 حالياً) يضمّن معرف الخدمة بصيغة Railway الرسمية للـcache-mounts:
```dockerfile
RUN --mount=type=cache,id=s/<SERVICE_ID>-/root/.m2,target=/root/.m2 \
```
- **المعرف يجب أن يطابق الخدمة الناشرة نفسها** (وثائق Railway: builds/dockerfiles — Cache mounts) — معرف v3 الحالي `30294a45-…` سيكون **خاطئاً** على الخدمة الجديدة.
- الإجراء: فرع إصلاح `fix/deploy-v4-cache-id` → كوميت واحد يبدّل المعرف القديم بالجديد → **PR** (بوابات CI كاملة) → الدمج بكلمة المستخدم («ادمج» — §14.3). هذا هو كوميت `bb6da39` من دورة v3 حرفياً.
- بديل الطوارئ للاختبار قبل الدمج: `serviceInstanceDeployV2(commitSha=<رأس الفرع>)` ينشر كوميت الفرع مباشرة دون انتظار الدمج (نفس ما فعلته دورة v3 لإثبات الإصلاح مبكراً).

### الخطوة 4 — نقل المتغيرات الـ45 (النقل الصادق)
القناة الرسمية لاسترداد القيم الحية من حساب v3 الحالي (قبل إخلائه):
```python
# الاسترداد (القناة الوحيدة للقيم — المنصة write-only في العرض):
mutation { variablesForServiceDeployment(projectId:"<v3>", environmentId:"<v3>", serviceId:"<v3>") }
# النقل إلى الحساب الجديد — العقد المقيس: الطفرة تستقبل input واحداً (VariableCollectionUpsertInput)
# لا أسماء عليا، وskipDeploys=true يؤجّل أي نشر إلى خطوة النشر الصريحة (لا نشر وسيط بقيم ناقصة):
mutation Vars($input: VariableCollectionUpsertInput!) { variableCollectionUpsert(input: $input) }
# input = { projectId, environmentId, serviceId,
#           variables: <كائن JSON حرفياً كما في السطر أعلاه — لا سلسلة نصية أبداً>,
#           replace: true, skipDeploys: true }
```
**التحذير المقيس (حادثة 5019 متغير):** تمرير `variables` كسلسلة `json.dumps()` يفسَّر حرفاً-حرفاً فيولّد آلاف المتغيرات المهملة. الصيغة الصحيحة **كائن JSON مباشر**. اختبر بمتغير واحد أولاً ثم نفّذ المجموعة الكاملة.
**التحقق العكسي بعد النقل:** عدّ الأسماء = 45 بالضبط، صفر نواقص، صفر زيادات (مقارنة مجموعة الأسماء قبل/بعد).

### الخطوة 5 — السجل الاسمي الدقيق للاستثناءات (سبع قيم معدلة + واحدة محذوفة، في خمس مجموعات — ليست نسخاً أعمى)
القياس الكامل لدورة v3: **سبعة متغيرات تغيّرت عن الحساب القديم + واحد حُذف**، و`DB_USERNAME` نُقل كما هو (لم يتغير). هذا الجدول هو **السجل الاسمي المرجعي** — أي ملخص أعلى درجة يربط إليه ولا يعيد سرداً ناقصاً. أعد التقييم نفسه عند كل تكرار:

| المجموعة | المتغيرات (الأسماء الدقيقة) | قرار v3 المقيس | ما يعنيه عند التكرار |
|---|---|---|---|
| نطاق (إلزامي) | `AUTH_SERVER_ISSUER` | أُعيد كتابته للنطاق الجديد | يحمل نطاق الخدمة الجديد — الصورة لن تقلع صادقة بدونه |
| نطاق (إلزامي) | `CORS_ALLOWED_ORIGINS` | كذلك | نفس عائلة النطاق |
| نطاق (إلزامي) | `OAUTH_CLIENT_REDIRECT_URIS` | كذلك (نمط BFF-redirect) | نفس عائلة النطاق |
| قناة القاعدة | `DB_URL` | أُعيد للقناة المباشرة + `channel_binding=require` | قاعدة Neon **خارجية لا تتغير** — القيمة تنتقل كما هي من حساب v3 الحي (هي أصلاً بالقناة الصحيحة الآن؛ انقلها كما هي) |
| هوية الترحيل | `SPRING_FLYWAY_USER` + `SPRING_FLYWAY_PASSWORD` | أُعيدتا ل`neondb_owner` (قياس psycopg: الاعتماد مقبول) | **قِس قبل النقل**: إن كانت اعتمادات Neon الحية مقبولة فانقلها كما هي |
| كلمة مرور التشغيل | `DB_PASSWORD` | بقيت على قيمة المستخدم المدوّرة (القديمة ميتة مقيساً 28P01×3) | قاعدة «اللازم الصحيح»: القيمة الحية العاملة تنتقل، الميتة لا — قِس قبل النقل |
| محذوف | `MAIL_FROM` | أُزيل (لا يقرؤه التطبيق — لا mapping ولا setFrom) | لا تنقله أصلاً على أي حساب |

(`DB_USERNAME` ليس من الاستثناءات: نُقل كما هو من الحساب القديم بلا تعديل.)

### الخطوة 6 — ضبط تكوين الخدمة (مطابقة v3 حرفياً)
```python
mutation { serviceInstanceUpdate(projectId:"<new>", environmentId:"<new>", serviceId:"<new>",
  dockerfilePath: "Dockerfile",
  healthcheckPath: "/actuator/health/liveness", healthcheckTimeout: 300) }
```
(الطفرات ترجع Boolean بلا selection — درس المخطط §7.)

### الخطوة 7 — النشر الأول والتحقق
- أدّى نشر main أن يدفع auto-deploy تلقائياً بعد دمج كوميت الخطوة 3، أو انشر يدوياً بـ`serviceInstanceDeployV2`.
- انتظر SUCCESS (أول بناء بارد ~25 دقيقة بالخبرة المقيسة؛ الأبنية التالية دافئة بالـcache-mount: قياس v3 = ~80 ثانية).
- **نفّذ قائمة الدخان §8 كاملة** — كل بنودها كانت خضراء على v3 لحظة الإقلاع الأول.

### الخطوة 8 — تحديث الـwatchdog للنطاق الجديد (كوميت ثانٍ في نفس الـPR أو PR تالٍ)
`watchdog.yml` يثبّت النطاق في `BASE_URL` — **اختبار البوابة `ProductionWatchdogFilesTest` يرفض أي نطاق آخر** (هذا مقصود: حارس يمنع النشر لنطاق لم يُحدث). كوميت `a755bb8` من دورة v3 هو النمط: حدّث `BASE_URL` + أي مراجع نطاق في ملفات الحقيقة. **ملاحظة:** خطوة freshness تقرأ commit status باسم سياق `<project-name> - <service-name>` — على مشروع اسمه `app-java-v3` وخدمة اسمها `app-java-v3` يبقى السياق `app-java-v3 - app-java-v3` كما هو؛ إن سمّيت مشروعك الجديد باسم مختلف فحدّث `RAILWAY_STATUS_CONTEXT` في الـworkflow أيضاً.

### الخطوة 9 — إخلاء الحساب القديم (v3)
- عطّل أي قنوات نشر متبقية (نمط تعطيل `fork-sync` بـ`disabled_manually` عبر GitHub API — أنجز لدورة v3).
- **استرداد المتغيرات الأخير قبل الإخلاء** (الخطوة 4 من حساب v3) — هذا هو أمانك الوحيد إن نسيت قيمة.
- اترك الحساب حتى نفاد رصيده أو احذفه من اللوحة بيدك (قرار المستخدم حصراً).
- **لا تحذف/تلمس Neon أو Upstash أو B2** — كلها خارج Railway وأصل القصة (§1).

## 6. السيناريو ج — الانتقال لمزوّد آخر (Render / Fly.io / Cloud Run / أي منصة حاويات)

> **المبدأ المقيس:** ما تبنيه Railway هو صورة Docker من Dockerfile **محايد للمزوّد بالتصميم** (تعليق Dockerfile نفسه: «the same Dockerfile stays portable») — منصة بناء خارجية ليست شرطاً.

**ما ينتقل كما هو بلا تعديل:**
1. **Dockerfile الرباعي** (بناء Maven → تدريب AOT → صورة تشغيل): يقرأ `PORT` من البيئة (أي منصة حاويات توفره) ويشغّل `java -jar` عبر ENTRYPOINT — لا شيء فيه خاص بـ Railway **عدا سطر cache-mount وحده** (خطوة 3 أعلاه — على مزوّد آخر إما أن يدعم cache-mounts بصيغة موسعة أو يُحذف السطر بسلاسة: تعليقه الأصلي يقول إنه «سطر cache عادي قابل للحذف دون قابلية النقل»).
2. **مجموعة المتغيرات الـ45** كاملة (§5) — كلها متغيرات تطبيق قياسية، لا شيء فيها خاص بـ Railway (متغيرات `RAILWAY_*` الـ11 محقونة تلقائياً من المنصة ولا تُنقل).
3. **مسار الفحص الصحي** `/actuator/health/liveness` + المهلة 300s — اضبطها في تعريف الخدمة على المنصة الجديدة (كلهامتر من تكوين الخدمة لا من الكود).
4. **قاعدة البيانات وRedis والبريد والوسائط** — خارجية أصلاً (§1)؛ صفر عمل.

**ما يحتاج تعديلاً محسوباً:**
1. **القيم الثلاث الحاملة للنطاق** (issuer/CORS/redirect) — تُكتب للنطاق الذي تمنحه المنصة الجديدة (أو نطاقك المخصص إن ربطت DNS — الخيار الأنظف طويلة الأجل لأنه يفك الارتباط بنطاق المنصة).
2. **خطوة freshness في الـwatchdog** — قراءة commit status عبر GitHub هي عقد Railway-API (سياق `app-java-v3 - app-java-v3` بواسطة تطبيق Railway GitHub). على مزوّد آخر إما أن يوفر webhook/status مكافئاً (Render/Fly يوفران deploy statuses عبر API خاصة بهما) فتُعاد كتابة الخطوة لقراءته، أو تُستبدل بعتبة عمر أبسط (نمط «حد عمر 240m» الموثق في `d43840d` — الـworkflow يملك هذا الفرع أصلاً لحالة غياب الحالة). **اختبارا البوابة (`ProductionWatchdogFilesTest`/`DeploymentChannelFilesTest`) سيفرضان التحديث** — هذا مقصود.
3. **قناة النشر**: على Railway كان auto-deploy من main عبر GitHub App — المنصة الجديدة لها آلية الربط المكافئة (Render: Auto-Deploy على branch؛ Fly: GitHub Action أو `flyctl deploy`) — اربطها بـ`main` وأبقِ نمط «الدمج بكلمة المستخدم ثم النشر تلقائي».

**ترتيب التنفيذ المقترح (نافذة انتقال بلا انقطاع):** المنصة الجديدة تُنشر أولًا بمجموعة المتغيرات كاملة وتتحقق منها قائمة الدخان §8 على نطاقها المؤقت، **ثم** تُبدَّل القيم الثلاث للنطاق النهائي — وهذه القيم **تُقرأ عند الإقلاع فقط** (بيئة Spring تُحل مرة واحدة عند بدء الحاوية)، فالتبديل **لا يسري على الخدمة الحية دون نشر جديد**: (1) أطلق نشراً صريحاً بعد تبديل القيم (نمط الخطوة 7 من §5) وانتظر SUCCESS، (2) نفّذ قائمة الدخان §8 **مرة ثانية على النطاق النهائي** — عقد الـOIDC/issuer وCORS لا يُصدَّقان إلا على النطاق الذي يحمله الـissuer الجديد، (3) حدّث `BASE_URL` ومراجع الـwatchdog للنطاق النهائي وتأكد من جولة سليمة عليه (نمط الخطوة 8 من §5). قاعدة البيانات تخدم المنصتين بالتوازي في أثناء النافذة (اتصال فقط، لا ترحيل)، فلا نافذة قطع أصلًا.
