## 1. المبادئ المعمارية الحاكمة (غير قابلة للتفاوض)

1. **Modulith لا مايكروسيرفس:** التطبيق مفاعل واحد بحدود وحدات مفروضة باختبارات Spring Modulith القائمة (رسميًا: docs.spring.io/spring-modulith/reference). فريق صغير + وكلاء AI + نشر Railway = المفاعل الواحد أرخص وأصدق. أي اقتراح «استخراج خدمة» يحتاج ADR يثبت فشل الحل داخل المفاعل أولًا.
2. **مصدر حقيقة واحد + إسقاطات:** كل حقيقة أعمال يملكها مجال واحد (جدول §2). التغذية والبحث والبطاقات إسقاطات تحمل `source-id + source-type + version/updated-at` وتعيد فحص المصدر عند الفتح والتنفيذ (رحلات §23.1). الإسقاط لا يقرر الحقيقة النهائية أبدًا.
3. **fit-gap قبل أي enum/جدول/سير عمل جديد:** مفردات الحالات في مواصفة الرحلات **دلالية مستهدفة** لا أوامر تنفيذ — تُطابق مع المقيس ثم تُوسع بترحيل آمن (رحلات §3.3 صراحة).
4. **الأحداث عبر حدود Modulith فقط:** لا استدعاء مستودع متقاطع بين الوحدات — عقد SPI في `marketplace-shared` وأحداث Spring Modulith (رسميًا: docs.spring.io/spring-modulith/reference/events.html) مع مستهلك مالك وidempotency عند الاستهلاك.
5. **العقد أولًا:** كل موجة تحدّث OpenAPI (springdoc القائم) قبل الكود، وبوابة التوافق الرجعي القائمة في CI تحرس القدامى — توسيع فقط (additive)؛ الكسر يتطلب إصدارًا معلنًا وقرارًا.
6. **الأخطاء عقدًا:** RFC 7807 `application/problem+json` موحدًا (رسميًا: rfc-editor.org/rfc/rfc7807) — عنوان وسبب وحالة HTTP متسقة عبر كل الوحدات؛ الواجهة تبني عليها مكتبة CMP-15..24.

## 3. استراتيجية عقود API (OpenAPI-first)

1. **الوصف الحي هو المصدر:** springdoc قائم يولد 107 مسارات من الكود — العقد يُقفل عند كل دمج عبر بوابة التوافق الرجعي في CI (خطوة مقيسة في Build & Test). القاعدة الرسمية: عقد الواجهة لا يتوسع صمتًا؛ كل موجة تحدّث الكود والوصف معًا في نفس الـPR.
2. **التسمية الموحدة:** موارد جمعية (`posts`, `businesses`, `local-knowledge`, `official-messages`)؛ حالات snake_case في الأجسام؛ أخطاء RFC 7807 بترميز `type` مستقر لكل عائلة أخطاء تقابلها CMP-19..24.
3. **التوسيع فقط:** إضافة حقول اختيارية ومسارات جديدة مسموحة؛ تغيير دلالة أو حذف = قرار إصدار معلن (فصل إهمال عن إنفاذ — خطة موحدة §8.3).
4. **قاعدة idempotency في العقد:** كل عملية كتابة حساسة تقبل مفتاح `Idempotency-Key` (النمط الرسمي المدعوم في Spring عبر مرشحات معيارية) — يحكم AC-03-02/AC-07-04/AC-10-05.
5. **الترقيم (Pagination):** keyset/cursor في كل قوائم الإسقاط (تغذية/بحث/إشعارات) بلا إزاحة — يحمي AC-02-01 (استقرار الترتيب بين الصفحات).

## 4. الهوية والثقة والأدوار (المرحلة 1 — موجة C-1)

**المقيس:** `UserRole {CONSUMER, PROVIDER, ADMIN}` + `ReviewerBadge`/`ReviewerTrustScore` (مراجعة المجتمع) + `MembershipVerificationState` + منفذا `NeighborhoodVerificationProvider` و`NeighborhoodTrustLookupPort` في shared + أحداث `MembershipVerificationGrantedEvent`/`UserRoleChanged`.

**المستهدف (يحكمه JT-12 + JT-01):**

1. **وقائع تحقق منفصلة عن الهوية:** جدول `verification_facts` (النوع: LOCAL_MEMBERSHIP / BUSINESS_OWNERSHIP / PROFESSIONAL / INSTITUTIONAL_DELEGATION؛ الحالة؛ الأدلة في مخزن سري لا في الملف العام) — كل نوع يثبت واقعة محددة فقط (رحلات §14.3). لا ترقية ضمنية: امتلاك واقعة لا يغير `UserRole` ولا يمنح صلاحية خارج نطاقها.
2. **قرار D-03 (الأدوار المتعددة):** ترحيل آمن من `UserRole` الأحادي إلى أدوار مستمدة من الوقائع والملكيات (المسار الأقل كلفة: جدول اعتمادات أدوار مرجعي يقرأه `method-security` القائم) — التصميم التفصيلي بعد fit-gap مع قواعد `@PreAuthorize` المقيسة في الوحدات.
3. **قرار D-02 (العضوية الموثقة):** واحدة نشطة (سلوك الخدمة الحالي) أم متعددة — ترحيلة واحدة تحسمه، والأحداث القائمة (منح/سحب) تُستهلك من الإسقاطات.
4. **اختبار سلبي إلزامي لكل فعل:** مصفوفة المرفوض (غير موثق، دور خاطئ، مالك خاطئ، حي خاطئ، حالة غير مؤهلة) في اختبارات التكامل — قاعدة «إخفاء الزر ليس أمنًا» (رحلات §20).

## 5. المؤسسات والرسائل الرسمية (P0 → المرحلة 4)

**الخطوة C-0 (بوابة كل ما بعدها):** توصيل `marketplace-institutions` — مسودة **#525** قائمة بالفعل: إضافته إلى `<modules>` + اعتماد `marketplace-app` + اختبار Modulith للحدود + دخان إقلاع مع الوحدة. تُراجع المسودة وتُستكمل بواباتها، لا تُستنسخ موجة موازية.

**ثم C-4 (يحكمه JT-10):**

1. **دورة حياة الرسالة:** DRAFT/REQUESTED → REVIEW_REQUIRED أو AUTHORIZED → ACTIVE → CORRECTED / WITHDRAWN / EXPIRED — منفصلة عن العاجل، واختيار التصنيف لا يمنح الصلاحية (AC-10-01).
2. **مصفوفة التفويض (رحلات JT-10 §12.4):** `institutional_delegation` (الجهة × الفاعل × نطاق جغرافي × نوع الرسالة × عاجل أم لا) — الناشر مخول بالسجل لا بالاسم.
3. **الاستهداف الجغرافي:** عبر `geo` + PostGIS (وفق docs/postgis-integration-plan.md القائم — قرار D-07 للعربية ينسحب على فهارس البحث الجغرافي) — التغطية تُختبر بحدود (AC-10-02).
4. **لا قناة إشعارات ثانية:** الرسائل الرسمية حدث أعمال عادي يستهلكه `notifications` القائم (رحلات JT-10 §12.1.8) — البث عبر كتالوج §7 هنا.
5. **التصحيح/السحب ينشر إبطالًا** لكل الإسقاطات (تغذية/بحث/AI) — الحالة المنتهية لا تُعرض نشطة أبدًا (AC-10-04، ومقيس أصلًا في V162 ‏`ai_withdrawn_sources`).

## 6. البحث والذكاء الاصطناعي (المرحلة 5 ثم 10)

**المقيس:** `search` (25 ملفًا) + `ai` (33 ملفًا، مطبوع ومنشور من #522) + مسودة **#529** (بحث PostgreSQL عربي + أنواع منشور سؤال/طلب صريحة — V166–V169 محجوزة فيها) + مسودة #524 (توحيد بحث AI مع التوجيه القانوني).

**خطة التنفيذ:**

1. **العقد الموحد أولًا (C-5):** `search` يملك عقد بحث موحدًا (أنواع المصادر + الفلاتر + النطاق + الأهلية) وadapters لكل مجال — كل مصدر يسجل `source-type/source-id/version` في النتيجة (رحلات §6.2.4). مسودة #529/#524 تُراجعان على هذا العقد وتُستكملان — لا تُعاد كتابتهما من الصفر ولا تُدمجان صمتًا.
2. **العربية (قرار D-07):** توحيد الألف/الهمزة/الياء/التشكيل في طبقة قاعدة البيانات (pg_trgm + توحيد مقيس — postgresql.org/docs/current/pgtrgm.html) مع مجموعة تقييم عربية موسومة مختبرة على AC-04-03؛ وجود كائن الإعداد يُتحقق منه فعليًا في قاعدة اختبار الإصدار (AC-04-04).
3. **سلم الذكاء الستّي (خطة موحدة §9):** (1) حتمي → (2) محرك بحث → (3) قرارات Jev/TypeSafe المهيكلة → (4) نموذج رخيص → (5) نموذج قوي → (6) درجات تقييم تحرس الجميع. القاعدة المقيسة من #522 تسري: **المسارات المطبوعة (chat HTTP contract + أدوات البحث) تُقرأ فقط من العقود القانونية؛ الأهلية والرؤية قبل النموذج وبعد الاسترجاع؛ الخاص/المخفي/المسحوب لا يدخل سياق النموذج (V162 يقيس المسحوب بالفعل).**
4. **المزود الحي:** تفعيل لاحق بمفاتيح بيئة فقط (قاعدة الأسرار §10) — `SPRING_AI_MODEL_CHAT` حاليًا `none` في الإنتاج وهذا هو السلوك الصحيح حتى قرار التفعيل.
5. **OpenSearch (قرار D-06):** خلف بوابة قياس التكلفة/الجودة/التشغيل مقابل خط أساس PostgreSQL مقيس — لا فهرسان متداخلان بلا مبرر مثبت (رحلات JT-04 §6.5).
6. **ترتيب تعلمي (المرحلة 10):** بعد خط أساس حتمي + مجموعة تقييم + بيانات عرض/تفاعل (خطة موحدة §10) — مع اختبار مثبت أن غياب التفاعل لا يصبح إشارة سلبية، وملف الاهتمامات قابل لإعادة البناء والحذف (بوابة المرحلة 10).

## 7. التغذية والإشعارات والأحداث (المراحل 3 و7)

### 7.1 التغذية (C-3 — رهن D-05)

- fit-gap أولًا: المستمع القائم `NeighborhoodListingEventListener` + تفضيلات الإشعارات الموضوعية يقرران هل يلزم وحدة `marketplace-feed` أم توسعة داخل مجال قائم — القرار موثق في سجل D قبل أي كود.
- القوائم الأربع (JT-02): الأحدث (keyset حتمي، استبعاد غير المؤهل) → المتابعة (مصادر صريحة) → الشائع (نافذة معلنة + مقاومة إساءة) → «لك» (متأخر خلف بوابة المرحلة 10).
- الانطباع حدث موحد بمعيار ظهور متفق عليه مع العميل، لا يكرر بإعادة طلب الصفحة (AC-02-07، رحلات §5.4 «الانطباع ≠ التسليم»).

### 7.2 كتالوج أحداث الأعمال (C-7 — يحكمه رحلات §21)

لكل حدث في الكتالوج: مستلم مؤهل + قناة + تفضيل + إلحاح + idempotency — يجرد في جدول قرار يقره المالك قبل التنفيذ (نفس منهج V158/V159/V164/V165 المقيس لأنواع التفضيلات):

`post.replied · post.mentioned · post.resolved · group.join-requested/decided · event.updated/cancelled · service-inquiry.received/updated · market-item.state-changed · official-message.published/corrected/withdrawn/expired · verification.state-changed · report.decided · recommendation.linked · knowledge.stale-detected/published/withdrawn · digest.daily-business`

- التوجيه عبر `notifications` القائم (قنوات inbox/بريد/WebSocket) — push بعد قرار D-10 (FCM/APNs رسميًا: firebase.google.com/docs/cloud-messaging · developer.apple.com/documentation/usernotifications).
- **at-least-once مع خفض تكرار مستهلك** — لا ادعاء exactly-once (رحلات §23.2) — ومفتاح idempotency يمنع الإشعار المكرر (AC-11-02).
- Quiet hours وdigest وفق D-26 — تجميع استفسارات الأعمال أولاً (فجوة P5).

## 8. حقوق البيانات والخصوصية الهندسية (C-1 — سد فجوة المراجعة)

الامتثال قرار قانوني مؤهل (D-15 — PDPL/GDPR بمدخل سعودي: sdaia.gov.sa)، والهندسة توفر القدرة:

1. **تصدير بياناتي:** مهمة غير متزامنة (قائمة قائمة في `platform-infra`) تجمع بيانات المستخدم من كل المجالات عبر منافذ SPI (لا استعلام متقاطع) → ملف موقّت بمدة صلاحية معلنة → تنزيل بضغط مالك مرة واحدة.
2. **التصحيح:** مسارات تعديل الملف والبيانات الشخصية بصلاحية صاحبها + تدقيق Envers (قائم مقيسًا في قواعد المستودع).
3. **الحذف/الإغلاق:** قرار أثر المحتوى (منشورات/توصيات/معرفة محلية) وفق سياسة احتفاظ معلنة (D-20): التوصية المعتمدة في الإجمالات تبقى مجهولة المصدر أو تُزال — القرار للمالك؛ الحساب يغلق بحالة نهائية والجلسات تبطل فورًا.
4. **خصوصية القياس:** المقاييس المسموحة فقط (رحلات §23.3)؛ سجل البحث مجهول الهوية للتقييم (رحلات §23.4)؛ لا حقول خام حساسة «لمجرد القدرة على جمعها».

## 9. الأمان الهندسي (يعمل عبر كل الموجات)

- **المصادقة قائمة ومقيسة:** OIDC + PKCE (edge) + JWT بمفتاح `marketplace-jwt-r3` — **دوران المفتاح قبل 2026-12-08** (التزام تشغيلي مفتوح من سجل النشر) عبر نفس نمط r2→r3 الموثق.
- **الأسرار:** Gitleaks (سياسة high/critical) مقيس في CI؛ المفاتيح متغيرات بيئة حصرًا (قاعدة مستودع مسجلة بعد حادثة المفتاح المصححة)؛ أي سر يظهر = إبطال فوري لا حذف كوميت فقط.
- **الصلاحيات:** `method-security` مكتمل من #511 (مقيس في عنوان الدمج) — كل فعل جديد يبدأ باختباراته السلبية (§4 هنا).
- **حد المعدل (429):** حد لكل مستخدم/نطاق على عمليات الكتابة الحساسة والبحث — يظهر للعميل برأس إعادة المحاولة (CMP-23).
- **سلاسل الفحوص:** CodeQL + Trivy + snyk القائمة تحرس كل موجة — لا استثناء جديد.

## 10. الموثوقية والتشغيل (المرحلة 11)

- **الرصد:** OTel قائم مع نقاط تصدير تحتاج تحديث `OTEL_*_EXPORT_URL` (مسجل تشغيليًا) — تكتمل به موجة C-11.
- **المراقبة القائمة:** watchdog الإنتاجي (قناة قياس freshness المقيسة) — تضاف إليه مقاييس الرحلات §11 في ملف UX عبر الأحداث الموحدة.
- **إعادة التشغيل والاسترداد:** اختبارات فشل نشر الأحداث + مستهلك معاد + إسقاط متقادم يُسترد (خطة موحدة بوابة المرحلة 11) — Testcontainers حقيقية لا نسخ مطابقة (قاعدة المستودع).
- **SLOs:** بعد خط أساس مقيس فقط — لا أرقام مختارة (رحلات §26.1).
