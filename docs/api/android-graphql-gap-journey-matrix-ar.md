# جرد فجوات رحلات Android وخريطة الانتقال الانتقائي إلى GraphQL

**المستودع:** waelhe/app-java-v3  
**تاريخ الفحص:** 16 أكتوبر 2026  
**النطاق:** Android، عقود REST الحالية، مخطط GraphQL، حالة طلبات السحب، والفجوات التي تمنع اكتمال رحلات المستخدم.  
**الغرض:** التمييز بين الوظائف المثبتة في main، والتغييرات المفتوحة، وفجوات المجال، وتحديد ما يستحق الانتقال إلى GraphQL دون إعادة كتابة REST بالكامل.

## 1. الخلاصة التنفيذية

1. عميل Android يستخدم Kotlin/Compose وRetrofit/Moshi؛ لم يكن Apollo Kotlin أو عمليات GraphQL موجودًا في اعتماديات Android والملفات التي جرى فحصها.
2. مخطط GraphQL صغير: service(id)، وservices(first, after) بترقيم محدود، وcreateService(input). لا توجد جذور للمجتمع أو الاكتشاف أو المتاجر والطلبات أو الرسائل.
3. اكتمال Phase 3 من DGS CodeGen لا يعني أن Android صار مستهلكًا لـGraphQL. الخطة تضع تكامل Apollo Kotlin وعقد SDL ذي الإصدار ضمن Phase 5، وتذكر أن Phase 4 تنتظر أمر مالك المشروع.
4. طلبا Android #591 و#593 مسودتان مفتوحتان وليسا جزءًا من main بحسب حالة GitHub التي فُحصت. لا تُعرض وظائفهما كأنها منشورة قبل مراجعة CI ودمجهما.
5. GraphQL لا يعوّض عقود مجال مفقودة. ربط التوصية بمصدرها الأصلي، والتجارة/الطلب والتسليم، وملفات مزودي الأعمال، والرسائل وحدود الخصوصية تحتاج عقودًا واستخدامات مجال أولًا.
6. الاتجاه المقترح هو GraphQL لقراءات الرحلات المركبة عندما يخفّض الطلبات الشبكية أو يوفر عرضًا موحدًا ذا أمان واختبارات، مع بقاء REST للعمليات التي يلائمها HTTP مباشرة.

## 2. الحالة المثبتة في المستودع

### Android وREST

واجهة MarketplaceApi.kt تحتوي على عقود للتسجيل والتحقق بالبريد ومفاتيح المرور، البحث والجغرافيا، عضوية الحي والتحقق، المنشورات والبحث والتعليقات والتفاعلات، الإعلانات المبوبة المحلية، الإشعارات، الفعاليات وRSVP، المجموعات والاستطلاعات. كما يوثق android/README.md أربعة أقسام رئيسية: الحي، السوق، العقار، ودليل الأعمال.

الحدود الموثقة في README مهمة:
- رحلة المتجر الكامل والسلة والطلب والتوصيل والدفع/إتمام الشراء ليست متاحة بالكامل لعميل Android.
- بحث دليل الأعمال يعيد عروضًا منشورة مع بعض بيانات تقييم المزود؛ لا يساوي ذلك دليلًا مكتملًا لملفات مقدمي الأعمال.
- رفع صور المنشورات يستخدم عقد رفع موقّع ورفع مباشر إلى التخزين ثم تأكيد الوسائط.
- قائمة الإشعارات وتعليمها كمقروء لا تثبت اكتمال تسجيل أجهزة Push وتسليم الإشعارات.
- قائمة المحادثات/Inbox والمراسلة المباشرة ليست رحلة Android مكتملة مثبتة.

### GraphQL

مخطط marketplace-app/src/main/resources/graphql/schema.graphqls يتضمن:
- Query: service(id: ID!): Service
- Query: services(first: Int, after: String): ServiceConnection!
- Mutation: createService(input: ServiceInput!): Service!
- Service وServiceStatus وServiceInput.

لا توجد عمليات في المخطط الحالي للمجتمع أو الاكتشاف أو المتاجر أو الطلبات أو الرسائل. وصول المستخدم المجهول إلى /graphql متوقع أن يعيد 401 ضمن عقد الأمان الحالي؛ لا يجوز فتح الوصول العام على مستوى endpoint دون سياسة عامة معتمدة واختبارات تفويض الحقول والكائنات.

## 3. مصفوفة الرحلات: العقد الحالي وقرار GraphQL

| رحلة المستخدم | الموجود حاليًا | الفجوة التي يجب عدم إخفائها | القرار |
|---|---|---|---|
| التسجيل والدخول ومفتاح المرور وOAuth/PKCE | REST/OIDC وCredential Manager وAppAuth | يظل اختبار الإعداد الحقيقي للمفاتيح والخروج النهائي أمرًا تشغيليًا منفصلًا | إبقاء REST/OIDC؛ GraphQL ليس بديلًا عن OAuth/OIDC. |
| الموقع وعضوية الحي والتحقق | geo tree/suggest وعضوية المستخدم والتحقق عبر REST | يجب إزالة بيانات الحي السابق عند تبديل النطاق، والتحقق من صلاحية العضوية | REST حاليًا؛ يمكن لاحقًا تجميع قراءة سياق المستخدم/الحي إذا أثبت القياس فائدة، مع اختبار عزل الأحياء. |
| موجز المجتمع والبحث عن المنشورات | feed وpost search بترقيم صفحات، وإنشاء منشور | لا توجد قراءة GraphQL للموجز؛ يلزم احترام أهلية المحتوى ونطاق الحي وحالات الإخفاء والحذف | مرشح مبكر لقراءة GraphQL مركبة؛ أوامر النشر تبقى في Use Case المالك ولا تنقل لمجرد توحيد التقنية. |
| تفاصيل المنشور والتعليقات والتفاعلات | قراءة التعليقات، إنشاء تعليق، الإعجاب والإلغاء عبر REST | البطاقة لا تكفي لإثبات صلاحية قراءة التفاصيل أو أن المحتوى ما زال ظاهرًا | يمكن لاحقًا قراءة التفاصيل والتعليقات والوسائط العامة المسموح بها في عملية مركبة؛ إبقاء أوامر التفاعل REST مبدئيًا. |
| صفوف الاكتشاف | عقد الاكتشاف موجود في الباك إند؛ ربط Android ضمن #593 المفتوح | sourceType/sourceId والمعاينة لا يثبتان وحدهما وجهة المصدر أو حالته الحالية أو صلاحية الإجراء عليه | مرشح قوي لأول Query بعد اعتماد الرحلة؛ حلّ المصدر إلى نوع معروف ومصرح به وإعادة التحقق عند فتحه. |
| البلاغات والتنبيهات العاجلة | عقدا REST؛ Android ضمن #591 المفتوح | لا يجوز الوعد بنتيجة إشراف؛ يجب ربط التنبيه بالحي والجهة المفوضة وفترة السريان | REST مناسب حاليًا؛ قد تدخل قراءة التنبيهات في الصفحة الرئيسية المركبة لاحقًا. |
| الفعاليات وRSVP | قائمة/إنشاء الفعاليات وتسجيل/إلغاء الحضور عبر REST | الحالة والسعة والأهلية يجب أن تأتي من الخادم؛ لا RSVP لحدث غير نشط | يمكن تركيب القراءة مع موجز الحي؛ تبقى أوامر RSVP REST مبدئيًا. |
| المجموعات وعضويتها | قائمة المجموعات والانضمام والمغادرة عبر REST | يلزم تحديد عضوية المجموعة وخصوصيتها، خصوصًا عند دعم مجموعات مؤسسات | قراءة مركبة محتملة بعد وجود عقد المؤسسة والخصوصية؛ أوامر join/leave تبقى REST. |
| الاستطلاعات والتصويت | قائمة/إنشاء الاستطلاع والتصويت وسحبه عبر REST | صلاحية التصويت وحالته النهائية يجب أن يقررهما الخادم | يمكن تركيب القراءة مع الموجز، مع إبقاء الأوامر REST مبدئيًا. |
| سوق الحي والإعلانات المبوبة | قراءة/إنشاء/سحب إعلان محلي عبر REST | الإعلان ليس متجرًا ولا يثبت وجود مخزون أو دفع أو طلب | يمكن إظهاره في قراءة سوق مركبة؛ لا تعرض عملية شراء غير مدعومة. |
| البحث عن الخدمات والعقار وعروض المزودين | /api/v1/search بمرشحات وترقيم؛ ListingSummaryDto يحتوي ملخص العرض وبعض بيانات التقييم | ملخص العرض لا يساوي ملف أعمال أو مراجعات مكتملة أو معلومات اتصال كاملة | مرشح لـGraphQL بعد تعريف ملف المزود والعرض والفلاتر والأذونات؛ افصل Business وOffer/Listing وPerson. |
| التوصية والعرض الأصلي | معاينة الاكتشاف تعرض نوع/معرّف المصدر وسبب الظهور | لا يثبت العقد وحده وجود رابط تفصيلي موثوق لكل مصدر أو أن العرض ما زال منشورًا | فجوة P0 قبل بناء إجراءات شراء/تواصل. عرّف حل مصدر نوعي، وحالات المصدر المنتهي/المحذوف والصلاحيات أولًا. |
| المتجر والسلة والطلب والتسليم | لا توجد دورة Android كاملة مثبتة | لا توجد رحلة مكتملة من المنتج إلى السلة والطلب والدفع والتجهيز والتسليم والإلغاء/الاسترداد | فجوة مجال وباك إند، لا مجرد فجوة SDL. ابنِ العقود واستخدامات المجال أولًا، ثم حدد قراءات وأوامر GraphQL المفيدة. |
| الإشعارات وPush | قائمة الإشعارات وتعليمها كمقروء عبر REST | تسجيل جهاز Push والتسليم ليسا رحلة مكتملة مثبتة | REST لإدارة الإشعار؛ لا تعتبر GraphQL subscriptions بديلًا تلقائيًا لـPush. |
| رسائل الجيران وInbox | لا توجد رحلة Android كاملة مثبتة | سياسة التواصل والموافقة والحظر والإبلاغ وحدود بيانات الجار غير مكتملة كرحلة | فجوة منتج وخصوصية مستقلة قبل GraphQL. معرفة المعرّف لا تمنح إذنًا لقراءة البيانات الخاصة أو بدء التواصل. |
| ملفات الأشخاص والأعمال والمؤسسات | بيانات محدودة عن المزود ضمن ملخصات البحث | يلزم فصل الحساب الشخصي عن الكيان والمفوّض والعرض، مع تحديد الحقول العامة والخاصة | مرشح لاحق لقراءة GraphQL مركبة فقط بعد اكتمال نماذج المجال وسياسات التفويض. |
| الوسائط والصور | URL موقّع ورفع مباشر ثم تأكيد عبر REST | الصور للعروض/المنتجات ليست ضمن الرحلة الحالية المثبتة | أبقِ الرفع REST وتخزين الملفات المباشر؛ GraphQL يعيد بيانات الوسائط المصرح بها فقط. |

## 4. سجل الفجوات حسب الأولوية

### P0 — تمنع تجربة مضللة أو غير آمنة

1. **ربط بطاقة الاكتشاف بالمصدر الأصلي:** عقد واضح لأنواع المصادر المدعومة، وقراءة التفاصيل، وإعادة التحقق من الحالة الحالية والصلاحية؛ لا يكفي وجود معرّف.
2. **الطلب التجاري وحالاته:** تحديد دورة الطلب ونتائج الدفع والتجهيز والتسليم والإلغاء/الاسترداد، مع حالات موثوقة وidempotency وسلوك فشل، قبل بناء واجهة شراء.
3. **خصوصية الجيران وموافقة التواصل:** فصل بيانات الحساب الخاصة عن الملف العام، وتعريف صلاحية الاطلاع والاتصال والحظر والإبلاغ.
4. **عقد مالي دقيق قبل توسيع التجارة والعقار:** المخطط الحالي يأخذ priceCents كـInt! (32-bit) ويرجع price كـFloat! بوحدات العرض. هذا ليس عقد أموال عامًا دقيقًا. اعتمد مبلغًا محدد الوحدة مع رمز عملة ISO 4217 وانتقالًا متوافقًا؛ لا تكسر الحقل الحالي بلا بوابة توافق.

### P1 — اكتمال عقد المنتج

5. **دليل الأعمال:** الانتقال من ملخصات العروض إلى ملف مزود موثوق مع فصل ملف الكيان والعرض والمالك/المفوّض والتقييمات.
6. **تفاصيل مصادر الاكتشاف:** حل موثوق للمنشورات والفعاليات والوظائف والعروض والإعلانات، مع معالجة المحذوف والمنتهي.
7. **الإبلاغ والإشراف والتنبيهات:** إكمال مراجعة #591 واختبار معالجة الأخطاء؛ الإبلاغ لا يعني أن المحتوى حذف، والتنبيه العاجل لا يساوي جميع أشكال البث المؤسسي.
8. **Inbox وPush:** عقد محادثات وموافقة وتسجيل الجهاز والتسليم غير مكتمل كرحلة Android.

### P2 — منصة GraphQL والعميل

9. **Phase 4:** الأمن على مستوى الحقل/الكائن، والتحقق، وحدود الموارد والصفحات، وModulith، والمعاملات/الأحداث والمراقبة — بوابات قبل توسعة SDL.
10. **Phase 5:** نشر SDL بإصدار من CI وإضافة Apollo Kotlin وتوليد العمليات من العقد المنشور، مع منع جلب SDL من الإنتاج أو نسخ المخطط يدويًا في بناء Android.
11. **حدود الكلفة والمراقبة:** الحد الأقصى للحجم والعمق والتعقيد والمهلة، وترقيم ثابت، واختبارات N+1/query count وقياس أداء فعلي.
12. **تجنب الترحيل الشكلي:** لا تُنقل عمليات HTTP المباشرة لمجرد توحيد التقنية.

## 5. ما يستحق الانتقال لاحقًا إلى GraphQL

ابدأ بقراءات محدودة تخدم رحلة حقيقية. لا تعتمد هذه الأسماء بوصفها SDL معتمدًا؛ هي مفاهيم مرشحة يجب أن تتبع اعتماد الرحلة والعقد.

1. **قراءة الصفحة الرئيسية/الاكتشاف:** صفوف مفعّلة ومصرح بها، ترتيب يقرره الخادم، سبب الظهور والإفصاح المدفوع وحالة المصدر. لكل صف ترقيم محدود ومستقر.
2. **قراءة صف اكتشاف بترقيم مؤشري:** فقط بعد إثبات دلالة المؤشر وترتيب المصدر. لا تسمِّ offset pagination بأنها keyset pagination.
3. **تفاصيل منشور/مصدر:** قراءة مركبة تجمع التفاصيل والتعليقات والوسائط العامة المسموح بها، مع حواجز الحذف/الإخفاء والخصوصية.
4. **بحث عروض وملف مزود:** بعد تعريف عقد ملف المزود ومراجعته وفلاتره. لا تدمج العقار والخدمات والمنتجات والإعلانات في كيان واحد غير مميز.
5. **سياق المستخدم والحي:** فقط إن أظهر القياس تكرار قراءات تستفيد من تركيبها، مع فصل الخاص والعام واختبارات العزل.
6. **قراءة السلة والطلب مستقبلًا:** بعد توفر دورة مجال كاملة؛ كل Mutation يفوض إلى Use Case الذي يملك المعاملة والحالة، ولا يضع قواعد الأعمال في resolver.

## 6. ما يبقى REST

- التسجيل وOAuth/OIDC ومفاتيح المرور وتبادل التوكن.
- طلب عنوان رفع الوسائط، والرفع إلى التخزين، وإكمال الرفع.
- Webhooks وcallbacks للتكاملات الخارجية والدفع.
- التنزيل/التصدير والعمليات ذات دلالات HTTP الواضحة.
- أوامر بسيطة لمورد واحد مثل التعليم كمقروء أو إرسال البلاغ، ما لم يوجد قياس يثبت فائدة حقيقية من نقلها.

يجب أن يستدعي REST وGraphQL Use Case واحدًا وقواعد عمل واحدة. لا تستنسخ قواعد المجال في طبقة GraphQL.

## 8. قواعد التصميم الحاكمة

- الخادم يملك أهلية المحتوى وترتيبه والنطاق الجغرافي؛ Android يعرض حالة الخادم ولا يخترعها.
- افصل الشخص والكيان والعرض والمعاملة والسياق. ظهور العرض في قناة معينة لا ينشئ نسخة جديدة منه ولا ينشئ معاملة.
- كل قائمة محدودة وذات ترتيب ثابت. لا استرجاع غير محدود ثم تقطيع في الذاكرة.
- لا يعتبر المعرّف إذنًا؛ اختبر الوصول إلى حي آخر وملف جار خاص وبيانات مالك/مفوّض.
- لا GraphQL subscriptions قبل اعتماد حالة استخدامها؛ مسار WebSocket لا يثبت وجود حاجة لآلية دفع ثانية.
- لا ترحيل شامل لـREST؛ تنقل القراءة أو العملية عندما تضيف التركيبة فائدة موثقة ومقيسة.
- عند التوسع استخدم DGS كنموذج GraphQL الوحيد كما تنص الخطة؛ تبقى وحدات المجال مالكة للقواعد واستخداماتها عبر SPI/Use Case، لا تعتمد على GraphQL أو مستودعات وحدات أخرى.
