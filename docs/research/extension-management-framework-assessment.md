# تقييم موثق لخيارات إدارة الإضافات في المنصة

**تاريخ التحقق:** 2026-10-23  
**الحالة:** تقييم أدلة وتوصية مقترحة للمراجعة؛ ليس اعتمادًا نهائيًا من مالك المنتج  
**المستودع المقاس:** `waelhe/app-java-v3`، `main` عند `ea0031a97db4452748a47582d3fed2c4d3ec1d52`  
**الملفات الحاكمة:** `SYSTEM.md`، `AGENTS.md`، `docs/governance/plans/saleor-dashboard-full-commerce-canonical-plan.md`، مع اتفاقية `docs/governance/feature-flags.md`  
**أثر الطبقات:** لا تغيير في كود الإنتاج أو الاعتماديات أو مخطط البيانات في هذا التقييم.

## 1. السؤال الذي يجب أن يجيب عنه التصميم

مصطلح «إضافة» يغطي ثلاثة احتياجات تقنية مختلفة. لا يقدم Spring Boot أو Spring Modulith وحدة واحدة جاهزة تجمعها كلها:

1. **تفعيل/تعطيل سلوك موجود ومبني داخل الإصدار الحالي.**
2. **تسجيل وتشغيل تطبيق مستقل جديد** يتكامل بعقد API وأحداث، ويمكن إظهار واجهته للمشرف.
3. **تحميل شيفرة Java جديدة داخل JVM وقت التشغيل** من JAR لم يكن موجودًا في الإصدار المنشور.

ينبغي تقييم كل نوع بأداته ومرجعه، وعدم تسمية علم ميزات قاعدة البيانات «نظام تثبيت إضافات»، أو اعتبار تنظيم Spring Modulith للوحدات دليلًا على إمكان تحميلها وإزالتها وقت التشغيل.

## 2. الحالة المقيسة في المستودع

### 2.1 إدارة السلوك الموجود

المكونات التالية موجودة بالفعل في `main`:

- `marketplace-shared/.../api/FeatureGatePort.java`: منفذ محايد بين الوحدات يتيح للمستدعي سؤال بوابة تشغيل في وقت الطلب، مع قيمة احتياطية يحددها المستدعي عند غياب السجل.
- `marketplace-console/.../FeatureFlag.java` و`FeatureFlagRepository.java`: سجل أعلام الميزات في قاعدة البيانات، بمفتاح فريد حي وحالة تشغيل.
- `marketplace-console/.../ConsoleService.java`: قراءة حالة العلم وقت الطلب، وتسجيل الأعلام وتغيير حالتها. واجهة الإدارة `ConsoleAdminController` محمية بـ`@PreAuthorize("hasRole('ADMIN')")`.
- `marketplace-app/src/main/resources/db/migration/V214__console_seed.sql`: يسجل خمسة أعلام لقدرات موجودة، وكلها تبدأ `enabled=TRUE` للحفاظ على السلوك الحالي. التعليق في الترحيل ينص صراحةً على أن العلم يصف قدرة موجودة ولا ينشئ الكود الذي ينفذها.

الأعلام الخمسة المزروعة هي `community.events.enabled` و`community.market.enabled` و`community.polls.enabled` و`community.lost-found.enabled` و`institutions.urgent.enabled`. وتستدعي خدمات المجتمع/المؤسسات `FeatureGatePort` لبعض هذه المسارات فعلًا؛ يجب أن يبقى التحقق من كل مستهلك محددًا بأسماء المفاتيح والاختبارات، لا تعميمًا على جميع وحدات المنصة.

وعليه، **القدرة الحالية هي التحكم التشغيلي في وظائف محددة موجودة**، وليست كتالوجًا شاملاً لحزم إضافات قابلة للتركيب. لا يثبت هذا السجل وحده أن كل المسارات التابعة لأي ميزة تتوقف عند إطفائها؛ يجب قياس المستهلكين والآثار الجانبية لكل ميزة.

المصدر المحلي: [FeatureGatePort](https://github.com/waelhe/app-java-v3/blob/main/marketplace-shared/src/main/java/com/marketplace/shared/api/FeatureGatePort.java)، [ConsoleService](https://github.com/waelhe/app-java-v3/blob/main/marketplace-console/src/main/java/com/marketplace/console/ConsoleService.java)، [FeatureFlag](https://github.com/waelhe/app-java-v3/blob/main/marketplace-console/src/main/java/com/marketplace/console/FeatureFlag.java)، [ترحيل V214](https://github.com/waelhe/app-java-v3/blob/main/marketplace-app/src/main/resources/db/migration/V214__console_seed.sql)، [اتفاقية Feature Flags](https://github.com/waelhe/app-java-v3/blob/main/docs/governance/feature-flags.md).

### 2.2 ما يدعمه Spring Boot وSpring Modulith

- شروط Boot مثل `@ConditionalOnProperty` و`@ConditionalOnBooleanProperty` تحكم إنشاء التهيئة/الفول وفق خصائص البيئة؛ وهي لا تمثل آلية عامة لتحميل JAR جديد أو إزالة Beans بأمان بعد بدء التطبيق. مصدر رسمي: [Spring Boot ConditionalOnBooleanProperty API](https://docs.spring.io/spring-boot/api/java/org/springframework/boot/autoconfigure/condition/ConditionalOnBooleanProperty.html).
- يدعم Spring Modulith اكتشاف الوحدات والتحقق من حدودها، وتشغيل `ApplicationModuleInitializer` عند بدء التطبيق عبر `spring-modulith-runtime`، وترتيب التهيئة حسب تبعيات الوحدات. هذا دعم لتهيئة وحدات التطبيق عند الإقلاع، وليس عقدًا موثقًا للتثبيت/التفريغ الديناميكي للوحدات. المصادر الرسمية: [Runtime Support](https://docs.spring.io/spring-modulith/reference/runtime.html)، [Verification](https://docs.spring.io/spring-modulith/reference/verification.html).
- لذلك يجب الاحتفاظ بآلية `FeatureGatePort` للتحكم التشغيلي حيث جرى توصيلها بالفعل، واستخدام Modulith لحدود الوحدات والأحداث والتحقق المعماري؛ لا ينبغي الادعاء بأن أيًا منهما يوفر متجر إضافات ديناميكيًا.

## 3. المرشح الأول لتحميل JAR: PF4J

يوفر [PF4J](https://github.com/pf4j/pf4j) بالفعل نموذج Java للإضافات المحملة من JAR/ZIP وقت التشغيل، مع `PluginManager`، ونقاط امتداد، ومحمّل أصناف منفصل، وحالات دورة حياة مثل `CREATED` و`DISABLED` و`RESOLVED` و`STARTED` و`STOPPED`. كما يدعم تعريف إصدار أدنى للنظام وتبعيات الإضافات. المصدران الأصليان: [PF4J Plugin documentation](https://pf4j.org/doc/plugins.html)، [PF4J lifecycle](https://pf4j.org/doc/plugin-lifecycle.html).

لكن **تكامل Spring ليس مبررًا لإضافة اعتماد الإنتاج حاليًا**:

- README الرسمي لـ[pf4j-spring](https://github.com/pf4j/pf4j-spring) يصف المشروع صراحةً بأنه *proof of concept* لتكامل PF4J مع Spring Framework.
- ملف البناء في الفرع الرئيسي للمستودع يثبت إعدادات `pf4j.version=3.13.0` و`spring.version=6.2.2` و`java.version=17`، مع إصدار أب `0.11.0-SNAPSHOT`. هذا لا يثبت أنه غير متوافق مع Spring Boot 4.1.1/Java 25، لكنه **لا يوفر دليل توافق إيجابيًا** لبيئتنا الحالية المبنية على Spring Framework 7 وسياق Boot 4.
- لم يُنفذ في هذا التقييم اختبار نموذج أولي باستخدام إصدارات المشروع المثبتة، ولذلك لا يجوز وصف PF4J-Spring بأنه جاهز للإنتاج لدينا.

المصدر القابل لإعادة الفحص: [pf4j-spring README](https://github.com/pf4j/pf4j-spring/blob/master/README.md)، [pf4j-spring pom.xml](https://github.com/pf4j/pf4j-spring/blob/master/pom.xml).

هناك أيضًا قيد أمني: محمّل الأصناف المنفصل ليس حد عزل أمنيًا للبرمجيات غير الموثوقة داخل JVM نفسها. إن كان المنتج سيسمح لأطراف خارجية بنشر شيفراتها، فالتشغيل في عملية مستقلة بحدود مصادقة وصلاحيات وشبكة أوضح من اعتبار JAR «معزولًا» أمنيًا.

**النتيجة:** لا نضيف PF4J أو PF4J-Spring إلى التبعيات الآن. يبقى PF4J مرشحًا لاختبار توافق محدد فقط إذا كان تحميل شيفرة Java داخل العملية حاجة منتج مؤكدة.

## 4. مرجع إدارة التطبيقات القابلة للتركيب: Saleor Apps

توضح وثائق Saleor الرسمية نموذجًا مختلفًا عن تحميل JAR:

- التطبيق كيان مستقل، ويُعرّف ببيان/Manifest.
- يطلب مجموعة صلاحيات محددة، ويوافق المسؤول على الصلاحيات عند التثبيت.
- يمكن تثبيته وإدارته وتفعيله أو تعطيله من لوحة الإدارة/GraphQL.
- يتكامل مع المحرك عبر API وWebhooks، ويمكنه توسيع لوحة الإدارة من خلال Mounting Points وواجهة مضمنة في iframe sandbox مع App Bridge.
- متجر التطبيقات بنقرة واحدة ميزة خاصة بـSaleor Cloud؛ أما الاستضافة الذاتية فتسمح بتثبيت التطبيقات يدويًا.

المصادر الرسمية: [Saleor Apps Overview](https://docs.saleor.io/developer/extending/apps/overview)، [Installing and Managing Apps](https://docs.saleor.io/developer/extending/apps/installing-apps)، [Extending Dashboard](https://docs.saleor.io/recipes/extending-dashboard)، [Extensions](https://docs.saleor.io/developer/app-store/overview).

لكن لا يعني هذا أن Saleor Apps الجاهزة تعمل مباشرة مع منصتنا. الخطة الحاكمة `D-SALEOR-FULL-001` تنص على أن Spring/DGS والوحدات الحالية هي أصحاب التنفيذ والحقيقة التجارية، وألا نشغل خادم Saleor ثانيًا. لذلك Saleor **مرجع سلوك معماري** لعقد التطبيقات والصلاحيات والتثبيت والـwebhooks وتوسعة الإدارة؛ أما بروتوكوله ومخططه الأصليان فلا يصبحان متوافقين تلقائيًا مع API منصتنا.

## 5. التوصية المستندة إلى المقارنة

هذه توصية مقترحة للمراجعة وليست تسجيلًا بأن مالك المنتج اعتمدها نهائيًا:

### المسار A — قدرات مبنية مسبقًا داخل التطبيق

استخدم آلية `FeatureGatePort` وسجل `feature_flags` الحاليين، بعد تدقيق المستهلكين الفعليين واختبارات الإطفاء. تبقى مفاتيح البيئة/شروط Boot لمتطلبات الإقلاع الثابتة فقط وفق `docs/governance/feature-flags.md`. لا تنشئ كتالوجًا ثانيًا لأعلام القدرات، ولا تحوّل العلم إلى ادعاء بأن حزمة جديدة قد ثُبتت.

### المسار B — إضافات يمكن تسجيلها وإدارتها دون إعادة نشر المنصة

اجعل المرجع الوظيفي هو **نموذج التطبيق المستقل على طريقة Saleor Apps**، لا تحميل JAR داخل عملية Spring:

1. تسجيل وصف إصدار التطبيق وعنوان Manifest ومعلومات التوافق.
2. إظهار الصلاحيات المطلوبة والموافقة الإدارية الصريحة عليها قبل التثبيت.
3. الاتصال بعقد المنصة المملوك لـSpring/DGS، مع توثيق المصادقة والصلاحيات والمهلات.
4. استخدام Webhooks/الأحداث مع توقيع، وسجل تسليم، وإعادة محاولة، ومنع تكرار الأثر.
5. تمكين/تعطيل تسجيل التطبيق والتكاملات من لوحة الإدارة، مع تحديد السلوك المتوقع للطلبات والأحداث القائمة عند تعطيله.
6. إذا كانت للإضافة واجهة إدارية، فاعتماد نمط iframe sandbox وApp Bridge كمرجع Saleor مع تكييفه لعقد منصتنا، لا نسخ App SDK كما هو.
7. إبقاء بيانات التطبيق وتاريخ تدقيق التغييرات محفوظة عند التعطيل، وعدم حذف بيانات نطاقات المنصة عند إزالة التكامل.

هذه قائمة متطلبات مشتقة من نموذج Saleor، وليست ادعاءً بأن هذا الإطار موجود بالفعل.

### المسار C — JAR ديناميكي داخل JVM

يُفتح فقط إذا أثبت متطلب المنتج أن تطبيقًا مستقلًا لا يلبي الحاجة. عندها يكون PF4J المرشح الأول للتقييم، عبر نموذج أولي قابل للحذف لا يدخل إلى main قبل إثبات:

- توافق البناء والتشغيل مع JDK 25 وBoot 4.1.1 وسلسلة التبعيات المثبتة.
- بدء/إيقاف/إعادة تشغيل الإضافة وإخلاء الموارد والمستمعين والمهام ومحمّل الأصناف فعلًا.
- توافق API وتبعيات الإضافات، والتعامل مع الإصدار غير المتوافق والفشل والرجوع للإصدار السابق.
- توقيع المصدر والتحقق من الحزم وSBOM ومراجعة CVE، مع عدم اعتبار محمّل الأصناف حد أمان.
- عدم تسرب معاملات قاعدة البيانات أو Beans الخاصة بالنواة إلى الإضافة على نحو يخالف حدود Modulith.

إذا فشل شرط التوافق أو العزل، فالبديل هو تشغيل الإضافة كعملية مستقلة، لا فرض تكامل Spring غير مثبت.

## 6. خارج النطاق في هذا التقييم

- لم تُضف أي اعتماديات.
- لم يُنشأ مخطط بيانات أو ترحيل Flyway.
- لم يُغيّر سلوك أعلام الميزات أو واجهات الإدارة.
- لم يُدّع أن كل مسارات الميزات الخمسة يمكن إيقافها بأمان قبل اختبار مستهلكيها.
- لم تُنسخ تطبيقات Saleor الجاهزة، ولم يُنشر خادم Saleor إضافي.
- لم تُجر تجربة PF4J مع Boot 4.1.1؛ التوافق ما زال غير مثبت.

## 7. الخطوة التالية المقترحة

بعد اعتماد المسار، تُنفذ شريحة مستقلة بالترتيب التالي:

1. **تدقيق إغلاق علم الميزات**: قياس جميع مستهلكي `FeatureGatePort` ومسارات REST/DGS والأحداث والمهام لكل علم حالي، ثم إضافة اختبارات تثبت توقف السلوك المطلوب.
2. **تجربة PF4J محدودة خارج main** فقط إذا كان تحميل JAR داخل JVM مطلوبًا صراحةً؛ لا تضف PF4J-Spring قبل نجاح مصفوفة التوافق.
3. **تنفيذ تسجيل التطبيقات الخارجية** على عقد Spring/DGS، مستوحى من Saleor Apps، إذا كان المطلوب هو إضافات يركبها مدير المنصة دون إعادة نشر الخادم.

بهذا يبقى قرار تحميل Java الديناميكي منفصلًا عن قرار «تثبيت تطبيق تكامل»، وتبقى آلية أعلام الميزات الموجودة هي مصدر الحقيقة لتفعيل وظائف المنصة المبنية مسبقًا.
