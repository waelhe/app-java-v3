# دليل التسليم — المنصة المجتمعية المحلية (ملف المطور ووكيل الذكاء الاصطناعي الحاكم للتنفيذ)

**الإصدار:** 1.0 — 2026-10-10  
**الغرض:** الملف الذي يمسك المسارات الثلاثة معًا ([إدارة المنتج](community-platform-product-management.md) · [UX](community-platform-ux-design.md) · [الباك-إند](community-platform-backend-execution.md) · [الجوال](community-platform-mobile-client.md)) في نموذج تسليم واحد: موجات، بوابات، تقارير قبول، مقاييس، برامج تشغيل، وسجل قرارات موحد — بحيث يعرف كل مطور وكل وكيل **ماذا يفعل الآن، بأي سلطة، وبأي دليل اكتمال**.  
**علاقة السلطة:** هذه الوثيقة لا تملك نطاق المنتج ولا قرارات تقنية — تملك *طريقة العمل* فقط. نظام إدارة المنتج يحدد Discovery/PRD/DoR/DoD؛ الخطة الموحدة تملك النطاق وسجل D، ومواصفة الرحلات تملك JT/AC/UJ، والعقود لخطة الباك-إند، والشكل لتصميم UX، والمرجع التقني الحاكم [خطة المطابقة الرسمية](official-compliance-plan.md).  
**الجمهور:** مطورون بشريون + وكلاء ذكاء اصطناعي (البروتوكول الإجباري §3 هنا = تفعيل AGENTS.md §0 القائم للمستودع).

## 1. نموذج التنفيذ — موجة واحدة = PR واحد

**مرجع مقارنة Nextdoor:** [community-platform-nextdoor-benchmark.md](community-platform-nextdoor-benchmark.md). يجب ألا تتحول تفاصيل البنية الداخلية غير المتحقق منها إلى متطلبات. انظر JT-18/AC-18 للخريطة والنطاق وJT-19/AC-19 للأخبار وحقوق الناشر.

1. **الموجة وحدة العمل:** كل عمود في جدول موجات الباك-إند §11 أو الجوال §9 = سلسلة PRs صغيرة داخل الموجة تنتهي بـPR الموجة الجامع، أو PR واحد إن صغرت — القرار بحجم التغيير لا بالذوق، والقاعدة الثابتة: **لا موجة تعمل بالتوازي مع موجتها التابعة قبل جاهزية عقدها** (خطة موحدة §26.1 شروط الترتيب).
2. **المكدس الحالي (مقيس 2026-10-10):** ‏`main` ← #532 (الخطة الموحدة) ← #534 (رحلات المستخدم) ← **هذه الموجة (المجموعة التنفيذية)**. تُدمج بالترتيب نفسه، وكل دمج بكلمة المالك الصريحة حصرًا (قاعدة المستودع §14.3 القائمة — الوكيل لا يدمج إلى main أبدًا).
3. **المراجعة قبل الدمج إلزامية:** اطلب CodeRabbit يدويًا عند الحاجة، وافحص نص نتيجة المراجعة وخيوطها؛ حالة check خضراء وحدها لا تثبت أن التحليل اكتمل إذا أعاد البوت رسالة rate-limit/action-not-completed. عند حد الاستخدام تُسجّل المراجعة «غير مكتملة» وتُستكمل بمراجعة بشرية موثقة قبل قرار الدمج. لا تُتبنى ملاحظات Greptile اللغوية بمفردها.
4. **بوابات الدمج القائمة لا تُستثنى:** الفحوص الستة (Build & Test ببوابة OpenAPI وGitleaks · Full Integration · CodeQL · Container Scan) + snyk + mergeable نظيف.

## 2. تعريف الإتمام لكل موجة (DoD الملزم)

موجة تُغلق فقط حين:

- [ ] كل فحوص CI خضراء على رأس الموجة بالضبط (قياس لحظي لا است recalled).
- [ ] مراجعة CodeRabbit/مراجعة بشرية فعلية مكتملة؛ صفر خيوط غير محسومة أو موثّق سبب رفضها. لا تفسر حالة check «success» التي تقول rate-limited/action not completed على أنها مراجعة ناجحة.
- [ ] **تقرير قبول رحلة** مرفق بالـPR بصيغة رحلات §30.1: معرفات JT/AC المغطاة · حقائق خط الأساس المقيسة (وحدات/ملفات) · نتائج المسارات الأساسية والسلبية · تغطية الترحيلات والأحداث · RTL/320px/قارئ الشاشة أو تصريح «غير منفذ» · سلوك فشل المزود · القرار المطلوب من المالك إن وجد.
- [ ] العقد محدث (OpenAPI) إن مسّ الواجهات، وبوابة التوافق خضراء.
- [ ] لا رقم ترحيلة جديد بلا قراءة حية لكل الفروع والإنتاج (باك-إند §12).
- [ ] الحقيقة بعد الدمج: **truth-sync** بتحديث PROJECT_MAP/SYSTEM §15 (النمط الحاكم المقيس لكل موجة دمج سابقة).
- [ ] ما تعذر اختباره موثق «غير مثبت» — لا اختبار أحمر يسمى أخضر (رحلات §28.2).

## 3. بروتوكول الوكيل (تفعيل AGENTS.md §0 — إجباري قبل أي إجراء)

```text
1. اقرأ: AGENTS.md (الإجبار النظامي) → SYSTEM.md §14.3/§15 → PROJECT_MAP.md → worklog
2. أعلن قبل الإجراء: [الملف الحاكم] من خريطة AGENTS.md §11 + [النواة المعمارية]
   + [بند مصفوفة الاتساق] + [أثر الحدود] + [دين: لا/نعم]
3. أعد قياس خط الأساس: رأس main + الفروع المفتوحة + أحدث ترحيلة + check-runs —
   لقطة PROJECT_MAP مؤرخة لا بديل عن قياس جديد (رحلات §0.3)
4. نفّذ أصغر شريحة تكمل خطوة حقيقية من رحلة (لا endpoint معزول بلا واجهة/نتيجة)
5. اختبر: المسار السعيد + المرفوض + الملكية/النطاق + التكرار/الفشل
6. سجل: تقرير القبول + القرارات الجديدة في سجل D (لا قرار صامت — رحلات §29)
7. اطلب: مراجعة CodeRabbit + كلمة المالك للدمج. لا دمج ذاتي.
```

قواعد السلوك الحاكمة (من الأمر المستمر للمالك): عمل متواصل بلا توقف لطلب إذن في التنفيذ الآلي؛ الوثائق والمستودعات الرسمية سلطة مطلقة لا يُفكر خارجها؛ أي انحراف/فجوة/تجاوز يُغلق فورًا ويوثق؛ لا رجوع لوثائق داخلية كمرجع تقني — مرجعية التقنية رسمية حصرًا.

## 4. تشغيل المقاييس (KPIs)

- جدول مؤشرات الرحلات **UX doc §11** هو السجل الوحيد للمقاييس — تُجمع من الأحداث المسموحة فقط (رحلات §25.3) عبر كتالوج أحداث الباك-إند §7.2.
- قاعدة خط الأساس: لا هدف رقمي يُعلن قبل قياس فعلي على نسخة تشغيلية (رحلات §28.1) — أول 30 يومًا بعد إطلاق كل رحلة = قياس فقط.
- **لوحة القراءة الشهرية:** مراجعة المالك لثلاثة أرقام فقط في كل جلسة: مؤشر الرحلة الأساسي، مؤشر النمو (الرحلات الجديدة المكتملة)، ومؤشر الجدارة (نسبة الإطلاق الممنوع §7 — يجب أن يظل صفرًا).
- قراءة التحليلات لا تُستخدم لتغيير سلوك حتمي بلا قرار منتج موثق (بوابة المرحلة 10 — خطة موحدة).

## 5. برامج التشغيل (عبور المسارات الثلاثة)

### 5.1 إقلاع الحي البارد (قرار D-21)

- **الواجهة:** UX doc §10.1 (فراغ صادق + نشاط مجاور موسوم + «كن أول من يشارك» + تعرّف على الحي).
- **التشغيل:** دليل تأهيل حي جديد (مسؤولية المالك): (1) بذر محتوى معرفي رسمي عبر JT-16 من مصادر جهات عامة؛ (2) دعوة أعمال الحي للمطالبة صفحاتها (JT-06)؛ (3) دعوة 2–3 مؤسسات للرسائل الرسمية (JT-10) بعد C-4. **لا بذر حسابات وهمية أو محتوى مصطنع إطلاقًا** (رحلات §24 (قاعدة عدم استخدام بيانات تجريبية في الإنتاج) «لا بيانات تجريبية في الإنتاج»).
- **الباك-إند:** استعلام «نشاط الأحياء المجاورة» وسيط معلن النطاق — ليس توسيعًا صامتًا (يحفظ AC-02-02).

### 5.2 حلقة الأسبوع الأول

- سلسلة إشعارات القيمة (3 كحد أقصى / 7 أيام — UX doc §10.2) تُنفذ كسياسات في كتالوج أحداث C-7 لا كاستثناءات كود.
- قياس أثرها مؤشر JT-01 الأساسي (% إكمال أول تهيئة) — لا عناصر أخرى قبل قراءة أولها.

### 5.3 وضع صاحب العمل (P5)

- Digest الاستفسارات (CMP-39 + حدث `digest.daily-business`) يمنع طوفان الإشعارات؛ الافتراضي يومي (D-26)؛ مؤشر JT-06 يراقب زمن الرد — إن تدهور بالتجميع يعاد ضبط الافتراضي بقرار موثق لا استثناء فردي.

### 5.4 حقوق البيانات (D-15/D-20)

- الفعالية عبر المسارات الثلاثة: APIs الباك-إند §8 + شاشات CMP-38 + إجراءات الاحتفاظ الموثقة — القرار القانوني للمالك بمستشار مؤهل قبل الطرح العام (خطة موحدة D-15 بنصها).

## 7. بوابة الإطلاق — قائمة الفحص التشغيلية (رحلات §28.2 منصّة)

يُمنع الإطلاق إذا وُجد أي من: محتوى خاص في بحث/AI/إشعار · معلومة متقادمة تظهر رسمية حالية · توصية تحولت تقييمًا/معاملة أو أنشأت سجلًا مكررًا · شارة منحت دورًا ضمنيًا · عاجل من غير مخول · رسالة مسحوبة «نشطة» · عنصر منتهٍ «متاح» · دفع/حجز ناجح زائف · إعداد غير صالح يكسر التطبيق · فشل بيئي «أخضر» · مرجع/خط أساس قديم بلا توضيح · تغيير عالي الأثر بلا تراجع. **كل بند له اختبار مقيس يقابله في موجته** — والقائمة تُقر قبل كل إطلاق رحلة بصيغة تقرير، لا بالذاكرة.
