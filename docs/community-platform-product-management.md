# نظام إدارة المنتج وتسليم المنصة المجتمعية المحلية

**الإصدار:** 1.0 — 2026-10-10  
**الغرض:** تحديد طريقة إدارة المنتج من الرؤية إلى رحلة مستخدم قابلة للقبول والقياس، وتوزيع القرارات والوثائق بين مدير المنتج والمالك ومطوري الباك-إند والجوال وUI/UX والاختبار والتشغيل. هذه الوثيقة عقد عمل وتشغيل، لا ادعاء بأن وظائف المنتج نُفذت.

## 1. المرجعية: ما المصدر الحاكم لكل سؤال؟

1. **توجيه المالك وسجل القرار:** يحكمان هوية المنتج والقرارات التي حُسمت أو بقيت مفتوحة؛ لا تحسم التوصيات قرارًا محفوظًا للمالك.
2. **مخطط المنتج والتجربة والمعمارية** (docs/product-platform-blueprint.md): يحدد نطاق المنصة المستهدف ومبادئ التكامل والمعمارية وخريطة شرائح التنفيذ.
3. **مواصفة رحلات المستخدم** (docs/community-platform-user-journeys.md): تملك الرحلات JT-01..JT-20 ومعايير القبول AC وحالات المستخدم والخصوصية والفشل والاسترداد.
4. **تصميم UX ونظام التصميم** (docs/community-platform-ux-design.md): يملك لغة العرض ومكونات CMP والشاشات والرموز وقواعد العربية/RTL والوصولية.
5. **سجل قرارات المنتج** (docs/platform-product-decisions.md): يميز قرارات المالك المثبتة عن الأمور المفتوحة، ولا يمنح توصية فنية سلطة قرار منتج.
6. **مرجع المقارنة مع Nextdoor** (docs/community-platform-nextdoor-benchmark.md): يصنف الأدلة العامة والثانوية والفرضيات، ولا يُعامل كدليل على التفاصيل الداخلية غير المنشورة.
7. **الكود وCI والنشر:** تثبت الحالة الحالية؛ أي لقطة PROJECT_MAP أو وصف PR تاريخي يُعاد قياسه قبل الاعتماد عليه.
8. **الوثائق والمستودعات الرسمية للإصدار المستخدم:** تحكم القرار التقني الخاص بالتقنية المعنية. لا يثبت المستند الداخلي أنه مسار رسمي، ولا يملك مرجع إطار برمجي قرار المنتج.

عند التعارض، يُسجل التضارب وصاحبه وأثره قبل التنفيذ. لا تُقدم اللقطة المؤرخة كقياس حي، ولا تُعلن المواصفة المستهدفة كوظيفة منشورة.
## 2. وظيفة مدير المنتج وحدود صلاحياته

مدير المنتج مسؤول عن **المشكلة والنتيجة والأولوية والتعريف القابل للقبول**، لا عن فرض حزمة تقنية أو رسم شاشة مسبقًا. يعمل كحلقة وصل يومية بين المستخدمين والمالك والتصميم والهندسة والتشغيل.

| المسؤولية | مخرجات يملكها مدير المنتج | حدود القرار |
|---|---|---|
| الرؤية والاستراتيجية | بيان قيمة المنتج، الجمهور الأول، النتائج التي سيغيرها المنتج، ما لن نبنيه الآن | اعتماد الرؤية وتغيير النطاق الأساسي للمالك |
| اكتشاف الحاجة | خطة بحث ومقابلات/اختبارات، الأدلة والافتراضات، فجوات الثقة والمحتوى المحلي | لا تُقدّم رأيًا أو منشور Nextdoor كدليل على طلب المستخدمين المحليين |
| تعريف التجربة | هدف الرحلة، تدفقها، حالات الفشل، متطلبات الخصوصية، AC قابلة للاختبار | لا يرسم عقد API أو يفرض schema من دون fit-gap |
| ترتيب العمل | Backlog مرتب بحسب قيمة المستخدم والمخاطر والتبعيات والجهد | لا يتجاوز بوابة قانونية/أمنية ولا قرارًا محفوظًا للمالك |
| التوافق بين الوظائف | التأكد من أن التصميم والعقد والخادم والجوال يتكلمون عن الرحلة نفسها | لا يخلق UJ أو قرار D في وثيقة منفردة |
| القبول والإطلاق | دليل AC، نتائج الاختبار والقياس، التوصية بالإطلاق/التأجيل | قبول المنتج لا يعوّض فشل الاختبارات أو التفويض الصريح للدمج/الإطلاق |
| التعلم بعد الإطلاق | لوحة مؤشرات، ملاحظات الدعم/البلاغات، سجل فرضيات وتجارب | لا يغير قواعد الأهلية أو ترتيب الثقة من بيانات تحليلات بلا مراجعة وقرار موثق |

إذا كان الشخص نفسه يؤدي دور المالك ومدير المنتج، تبقى **الوظيفتان متميزتين في سجل القرار**: التوصية والأدلة شيء، واعتماد المالك الصريح شيء آخر.

## 3. تعريف هوية المنتج ونتيجته

**صياغة العمل المقترحة:** شبكة محلية موثوقة تساعد الناس على العثور على معلومات حيّهم، وطرح حاجاتهم، والوصول إلى الأشخاص والخدمات والفرص المحلية، مع وضوح مصدر المعلومة وحدود الثقة.

هذه صياغة عمل وليست قرارًا باسم العلامة أو السوق النهائي؛ الاسم ما زال تحت القرار D-01.

المجالات الثلاثة مترابطة لكنها ليست سجلًا واحدًا:
- **المجتمع:** أسئلة وطلبات وتوصيات ونقاشات ومجموعات وفعاليات.
- **السوق المحلي:** سلع مستعملة ومجالات متخصصة تُفعّل وفق الجاهزية.
- **دليل الأعمال والجهات والمعرفة المحلية:** صفحات أصلية للأعمال/الجهات، ومعرفة محلية لها مصدر وحداثة وتصحيح.
- **الربط بين المجالات:** إحالات إلى السجل الأصلي، لا نسخ بيانات بين المنشورات والبحث والبطاقات.

وعد المنتج يُختبر برحلتين تكامليتين أساسيتين بالإضافة إلى رحلات السلامة:
1. **JT-16 تعرّف على الحي:** معلومة نافعة ← مصدر/حداثة ونطاق ← اقتراح تصحيح عند الحاجة ← مراجعة وصلة البحث.
2. **JT-17 توصية إلى خدمة:** سؤال/توصية ← سجل النشاط/الخدمة الأصلي ← فهم الثقة والتوفر ← قناة تواصل متاحة ← حالة حقيقية إذا كان الطلب قابلًا للتتبع.
3. **JT-10 الرسائل الرسمية:** جهة مفوضة ← رسالة ذات مصدر ونطاق وسريان ← تصحيح/سحب ينعكس على كل الأسطح.
4. **JT-12/JT-13 الثقة والسلامة:** واقعة تحقق محددة، أو بلاغ/مراجعة/استئناف بصلاحيات وتدقيق.

لا تُختزل قيمة المنتج في عدد الميزات، أو عدد الشاشات، أو عدد endpoints.

### 3.1 مرجع المقارنة مع Nextdoor: ما الذي كان ينبغي أن يدخل التصميم منذ البداية؟

المرجع التفصيلي هو [تحليل المنتج والبنية المعلنة وغير المؤكدة لـNextdoor](community-platform-nextdoor-benchmark.md). يجب أن تظهر منه صراحة أربعة مبادئ في PRD والرحلات: (1) المكان له حدود وأهلية منفصلتان عن نطاق البحث أو المتابعة؛ (2) التغذية لها طرق عرض مفهومة ومصدر سبب الظهور؛ (3) الأخبار والرسائل الرسمية والتنبيهات ليست نوعًا واحدًا من الثقة أو التفويض، والخريطة سطح عرض مكاني لا مصدر حقيقة؛ (4) توصيات Ask/Faves تُربط بمصادر وسجل نشاط أصلي، ولا تُعامل كتوثيق أو مراجعة مكتملة.

لا تُعتمد تفاصيل مثل Metablocks أو مكتبات iOS/Android أو توزيع Django/Go/Memcached/AWS في الخطة المستهدفة دون مصدر أولي حديث. الدرس المعماري المنشور عن Postgres/GIS يبرر قياس الاختناقات قبل الفصل إلى خدمات، ولا يبرر نسخ بنية Nextdoor إلى مشروع Spring modular monolith.

### 3.2 قرار المنتج: مسارات اكتشاف موضوعية شخصية فوق سجل محتوى موحّد

التوصية المنتجية هي أن تكون صفوف الصفحة الرئيسية **مداخل اكتشاف إلى محتوى أصلي**، وليست أقسام بيانات أو نسخًا منشورة من السجل نفسه. ويظل للمستخدم طريق واضح ومتوقع إلى «المتابعة»، وطريق منفصل إلى «لك/اكتشف لك»؛ لا يجوز أن تلغي نتيجة التخصيص ما اختار المستخدم متابعته صراحة.

### عقد الصفوف المقترح

| المسار/الصف | ما يعرضه | ضابطه |
|---|---|---|
| **تنبيهات مهمة للحي** | تحذير سلامة/طقس/انقطاع/خطر محلي مؤهل | مساحة بارزة خارج ترتيب الصفوف العادية؛ مصدر وصلاحية ونطاق وسريان واضحون؛ لا شعبية ولا نموذج ترتيب يقرر الأهلية |
| **آخر ما نشرته مصادر أتابعها** | أشخاص وصفحات أعمال ومجموعات ومصادر يتابعها المستخدم | لا يختلط بـ«اكتشف لك»، ويعرض المصدر ووقت النشر |
| **المفقودات والعثور عليها** | بلاغات نشطة ذات نطاق وحداثة مناسبين | مرشحات مكان/وقت/حالة؛ المستعاد أو المحلول لا يظهر كبلاغ نشط |
| **توصيات الجيران** | أسئلة توصية وردودًا منسوبة وروابط إلى ملفات الخدمات الأصلية | لا تُسمّى التوصية توثيقًا ولا مراجعة تجربة ما لم تستوفِ عقد ذلك النوع |
| **فعاليات وفرص قريبة** | فعاليات ومبادرات ومساعدة/تطوع وفرص مجتمعية أو عروض مؤهلة | الحالة والمكان ووقت الانتهاء ظاهرة |
| **اكتشف لك** | عناصر خارج المتابعة المباشرة اختيرت لاهتمام معلن أو إشارة محلية مفسّرة | سبب الظهور قابل للعرض والتعديل؛ النطاق الأبعد لا يدخل بصمت |

هذه أمثلة تصميم وليست ترتيبًا ثابتًا أو التزامًا بإظهار جميع الصفوف. يظهر الصف عندما تتوفر عناصر مؤهلة بالعدد/الجودة الكافيين وفق حد يختبر ويُضبط؛ الصف الفارغ يُحذف أو يستبدل بحالة صادقة، لا بمحتوى مصطنع. «عرض الكل» يفتح صفحة موضوعية كاملة مع فلاتر مناسبة، لا يكتفي بتمرير أفقي إضافي.

### الأبعاد التي يجب ألا تُختزل في تصنيف واحد

| البعد | أمثلة | وظيفته |
|---|---|---|
| غرض/نوع المحتوى | سؤال، طلب، توصية، استطلاع، مفقودات، عام، إعلان مصنف | يحدد القصد الأساسي وسير العمل |
| الموضوع | حيوانات أليفة، سكن، مطاعم، صحة مجتمعية، تعليم، رياضة | قد تكون للمحتوى موضوعات متعددة |
| النطاق المكاني | الحي، أحياء مجاورة، مدينة/منطقة خدمة | أهلية مكانية صريحة وليست مجرد إشارة ترتيب |
| المصدر والعلاقة | شخص/صفحة/مجموعة متابَعة، اكتشاف جديد، ناشر أو جهة مخولة | يفسر أصل العنصر وعلاقة المستخدم به |
| دورة الحياة | نشط، عُثر عليه، محلول، منتهٍ، مصحح، مسحوب | تحدد ما إذا كان العنصر مؤهلًا للعرض الآن |
| الاستعجال والثقة | عادي، يحتاج متابعة، تنبيه عاجل مخول؛ مصدر مجتمعي/رسمي | الاستعجال والتفويض وقائع مستقلة عن الشعبية والموضوع |
| الصفة التجارية | عضوي أو إعلان مدفوع معلّم بوضوح | يمنع شراء ترتيب أو تزكية عضوية ضمنية |

في لقطة خط الأساس المقيسة، قيم `PostCategory` الحالية هي `GENERAL` و`CLASSIFIED` و`LOST_FOUND` و`RECOMMENDATION`؛ لا توجد `QUESTION` و`REQUEST` في ذلك الأساس، وPR #529 كان يحمل اقتراحًا يحتاج إعادة قياس ومراجعة قبل الدمج. كما أن هذا enum القائم لا يغني عن أبعاد الموضوع والمصدر والنطاق ودورة الحياة والاستعجال. **لا تُضاف قيمة enum لكل موضوع أو مصدر أو حالة**؛ يُجرى fit-gap أولًا، ويُحافَظ على دلالات الكود القائم حتى قرار متوافق مع المالك والمطور.

### ترتيب القرار من الأهلية إلى العرض

1. **الأهلية الحتمية أولًا:** حالة المصدر والنشر/الإشراف والرؤية والصلاحية والنطاق المكاني ودورة الحياة والتفويض. لا يمكن للبحث أو التخصيص أو AI تجاوز أي شرط منها.
2. **استرجاع المرشحين:** عبر عقد البحث القانوني وadapters للمجالات المالكة. PostgreSQL هو خط الأساس المقيس في الخطة؛ استخدام OpenSearch ليس قرارًا سابقًا للقياس، بل بوابة D-06 للتكلفة والجودة والزمن والتشغيل.
3. **تكوين الصفوف وإزالة التكرار:** يعود كل عنصر إلى مفتاح سجله الأصلي (نوع المصدر + معرّفه/إصداره). يجوز أن يكون السجل مؤهلًا لأكثر من سياق اكتشاف من دون نسخه في قاعدة البيانات؛ ويمنع عقد العرض تكرار العنصر بلا داعٍ داخل الصف نفسه أو تسجيل انطباع مكرر عند إعادة الجلب.
4. **الترتيب:** مسارات «الأحدث» و«المتابعة» قابلة للتفسير وحتمية وفق قواعد معلنة؛ «الشائع» له نافذة زمنية ومقاومة إساءة. لا ينتقل «لك» إلى ترتيب متعلم إلا بعد خط أساس ومجموعة تقييم وبيانات كافية (D-13).
5. **الرجوع إلى الأصل:** كل بطاقة تبيّن المصدر والوقت والنطاق والحالة، وتفتح السجل الأصلي المملوك للمجال. الإسقاط في التغذية أو البحث لا يملك الحالة النهائية ولا ينسخ التعليقات/المراجعات/الخدمة.

**إشارات اختيار الصفوف وترتيب العناصر:** الاشتراكات والمتابعات الصريحة، الاهتمامات التي يعلنها المستخدم، التفاعلات ذات المعنى عند توفر تفسير صالح لها، والنطاق الجغرافي الذي اختاره/سمح به المستخدم. كثافة المحتوى المؤهل وحداثته تؤثران أيضًا في إظهار الصفوف. يجب الفصل بين (أ) أهلية الصف وظهوره، (ب) اختيار المرشحين داخله، (ج) ترتيب العناصر المؤهلة؛ ولا تتحول مشاهدات أو نقرات خام أو بلاغات سلامة إلى حقيقة عن اهتمام المستخدم. تُعرض أسباب التخصيص وتتاح إدارة الاهتمامات/إخفاء المصادر حيث تدعم الرحلة ذلك.

### دور الذكاء الاصطناعي وحدود الدليل

- يُنفذ التصنيف الواضح من بيانات المنشور واختيارات صاحبه وقواعد المجال الحتمية؛ لا يُستدعَ نموذج لكل منشور ليقرر أين يظهر.
- عند غموض حقيقي في النص يمكن تجربة نموذج منخفض التكلفة لتفسير الغرض/الموضوع، مع تقييم دقة عربي ومراقبة التكلفة وفشل آمن. ناتج النموذج **اقتراح تصنيف** يحتاج تحققًا/سياسة، وليس صلاحية أو حقيقة رسمية.
- لا يُعطى `JevModelRouter` أو أي نموذج سلطة الأهلية أو التفويض أو إعلان «عاجل»؛ يثبت أي توجيه/حكم منظم عبر عقد خرج واختبارات فعلية قبل وصفه بميزة منفذة. النموذج الأعلى تكلفة مخصص لتحليل متعدد المصادر أو خلاصة معقدة فقط إن ثبتت الحاجة، مع إظهار إحالات إلى السجلات الأصلية.
- توصية الجيران أو الخلاصة لا يجوز أن تخترع تجربة أو تزكية أو تثبت موثوقية عمل بلا دليل. تعرض الأدلة/الروابط والتواريخ، وتفشل إلى نتائج مصدرية قابلة للفتح إذا تعذر التلخيص.
- الإعلان المدفوع موسوم ومفصول عن التوصية العضوية في كل الصفحات، ولا يشتري أهلية أو شارة ثقة.

### معايير منتج يجب أن تدخل PRD والقبول

يقيس الفريق توافر العناصر المؤهلة لكل صف، ونسبة فتح الصفحات الموضوعية وإنجاز المهمة، وتغطية مصادر المتابعة، وتكرار ظهور/انطباع السجل ذاته، والإخفاء/«لست مهتمًا»، ووقت إيصال التنبيه المؤهل، ونسبة النتائج القديمة/المحلولة التي تظهر خطأ (الهدف صفر)، ودقة أي تصنيف/ملخص AI على مجموعة اختبار عربية معروفة. لا يُفسر عدم النقر على أنه عدم اهتمام، ولا تحول بلاغات السلامة إلى إشارة تفضيل.

## 4. دورة إدارة المنتج من الحاجة إلى الإصدار

### الخطوة A — اكتشاف الحاجة (Discovery)

قبل تصميم الحل، يوثّق مدير المنتج:
- من المستخدم المستهدف، وما المهمة التي يحاول إنجازها، وما سياقها المحلي/الجغرافي.
- دليل الحاجة: مقابلة أو اختبار أو بيانات دعم/سلوك مشروعة؛ التاريخ والعينة وحدودها.
- الوضع الحالي والبدائل والمشكلة الأشد؛ أثر الفشل أو المعلومة الخاطئة.
- ما نعرفه وما نفترضه وما يحتاج قرارًا أو اختبارًا.
- أثر الخصوصية والسلامة والشمول والبلدان المستهدفة.

مصادر Nextdoor المنشورة أمثلة لسلوك منتج مُعلن، وليست بديلًا عن بحث المستخدمين الفعليين في سوق المنصة.

### الخطوة B — تعريف المتطلب (Product brief / PRD)

لكل شريحة تنفيذية، يرفق PRD قصير يحتوي:
1. المشكلة ودليلها، والجمهور والنطاق والنتيجة المتوقعة.
2. الرحلة JT ومعايير القبول AC المتأثرة وسجل شاشات UJ ذي الصلة.
3. ما يدخل النطاق وما يستبعد منه بوضوح.
4. السيناريو الأساسي والبدائل وحالات الخطأ والعودة والتعامل مع المحتوى القديم/المسحوب.
5. الصلاحيات والملكية والجغرافيا والثقة والخصوصية والبيانات المحتفظ بها.
6. القيود غير الوظيفية: الأداء، الوصولية، RTL، أمان السجلات، التكرار، قابلية التشغيل.
7. المقاييس وخط الأساس وطريقة القياس، وحد الإيقاف/عدم الإطلاق.
8. التبعيات والقرارات المعلقة والمالك وموعد الحسم، لا قرارات مضمنة صامتًا.
9. مراجع المصدر الرسمية/التقنية وما الذي تثبته تحديدًا.

### الخطوة C — مراجعة الملاءمة (Fit-gap)

يعقد مدير المنتج مع التقنية والتصميم مراجعة مشتركة قبل اعتماد الحل:
- ما السجل/الوحدة/API الموجود فعلًا؟ ما الذي يملكه؟ وما الذي لا يثبته القياس؟
- هل يمكن إكمال الرحلة بتمديد الموجود بدل إنشاء نموذج أو وحدة جديدة؟
- ما مخاطر التوافق والترحيلات وترتيب الموجات وحدود الصلاحيات؟
- هل تدعم البيئة والمزودات الحالية الادعاء؟ هل المطلوب شاشة فقط أم معاملة قابلة للتتبع؟
- تُكتب الفجوة وقرارها ودليلها في PR/سجل الخطة، مع تحديث baseline مؤرخ.

### الخطوة D — التصميم والتحقق مع المستخدم

يحوّل UX الهدف إلى تدفق ومعلومات ونماذج وحالات، وليس صورًا جميلة فقط. يختبر نموذجًا أوليًا مع مستخدمين ممثلين للسياق واللغة والشاشة، ويشارك النتائج مع مدير المنتج والباك-إند والجوال. قبل البناء، يجب أن يعرف الجميع UJ وAC ومتى يكون السلوك «غير متاح» بدل نجاح متخيّل.

### الخطوة E — تنفيذ شريحة عمودية

تغلق الشريحة مسارًا صغيرًا حقيقيًا عبر الطبقات التي تحتاجها: واجهة/عقد API/خدمة/قاعدة بيانات/صلاحية/حدث/قياس حيث ينطبق. لا تُعتبر endpoint منفردة أو بطاقة تصميم أو DTO مولد إنجازًا لرحلة كاملة. يعتمد الترتيب على تبعيات موجات C وM وبوابات الخطة الموحدة.

### الخطوة F — التحقق والقبول

قبل إغلاق PR: اختبار الحالات الأساسية والسلبية والخصوصية والملكية والجغرافيا والتكرار والسحب/الانتهاء وفشل المزود بحسب الرحلة؛ مراجعة UI/UX/RTL/الوصولية؛ نتائج CI على commit محدد؛ ومقارنة AC مع الأدلة. كل عنصر لم يُختبر بسبب بيئة غير متاحة يبقى «غير مثبت» لا «ناجحًا».

### الخطوة G — الإطلاق والتعلم

الإطلاق محدود ومراقب وفق سياسة المالك. تُقاس المهمة الأساسية، والأخطاء، والاسترداد، والبلاغات، وأثر الإطلاق على الثقة والخصوصية. يقارن مدير المنتج النتائج بخط الأساس، يضع تفسيرًا ودرجة يقين، ثم يوصي بتحسين/تراجع. لا يُعلن هدف رقمي قبل خط أساس مقيس أو عينة كافية.

## 5. ترتيب الأولوية

تستخدم P0/P1/P2 الموجودة في خطة الرحلات، مع كتابة السبب دائمًا:
- **P0 — بوابة سلامة/نزاهة/اعتماد:** تسرب بيانات، خطأ صلاحيات، خط أساس/ترحيل يمنع البناء أو النشر، الرسائل الرسمية، أو فشل يضلل المستخدم.
- **P1 — القيمة الأساسية:** إنجاز رحلة متكررة مثل سؤال يصل لحل، الوصول إلى معلومة موثوقة، أو الوصول من توصية إلى مزود.
- **P2 — تحسين أو توسع:** تخصيص متقدم، تجميلات، خيارات سوق أو ميزات لا تعتمد عليها الرحلة الأساسية.

داخل المستوى نفسه، تُراجع قيمة المستخدم، وحجم الضرر عند الخطأ، وثقة الأدلة، والتبعيات، والجهد/تكلفة التشغيل، وقابلية التراجع. يمكن استعمال RICE أو تقدير أثر/ثقة/جهد كأداة مناقشة، لا كآلة قرار ولا بديل عن القانون والأمن.

لا تُرفع الأولوية لمجرد أن الميزة موجودة في Nextdoor، أو أن بناءها سهل، أو أن عدد التفاعلات قد يزيد.

## 6. سجل القرار والحوكمة

**سجل قرارات المنتج في docs/platform-product-decisions.md هو المرجع المفتوح/المعتمد؛ عدّل السجل عند القرار الصريح.** لكل قرار:
- المعرف والعنوان والحالة: PROPOSED / APPROVED / REJECTED / DEFERRED.
- صاحب القرار، وصاحب الإعداد، وتاريخ القرار.
- البدائل المتاحة، والدليل/المراجع، وأثر كل بديل على الرحلات والكلفة والمخاطر.
- الرحلات والوحدات وموجات C/M التابعة.
- شروط المراجعة/الرجوع/إعادة الفتح.

القرار D-17 حُسم باختيار Android أصلي؛ القرارات D-18..D-31 تبقى مقترحات إلى أن يحسمها المالك، ولا تتحول إلى اختيار نافذ عبر تكرارها في خطة جوال أو UI:
- D-17 منصة العميل: Android أصلي Kotlin + Jetpack Compose (قرار المالك)
- D-18 اللغة الإضافية
- D-19 سياسة القاصرين/العمر
- D-20 أثر حذف الحساب وحقوق البيانات
- D-21 الإقلاع البارد للمناطق قليلة النشاط
- D-22 عائلة الخط
- D-23 الوضع الداكن
- D-24 التقويم/الأرقام
- D-25 الهوية البصرية
- D-26 ساعات الهدوء وتجميع الإشعارات
- D-27 عقد/كتالوج أحداث المجال
- D-28 إدارة حالة العميل
- D-29 نطاق الخريطة والجغرافيا: حدود الأحياء، مصدر البيانات، النطاقات وأولوية مزود الخريطة.
- D-30 مصادر الأخبار المحلية: اعتماد الناشرين وحقوق التوزيع/الإسناد والتحديث والتصحيح والسحب.
- D-31 عقد الصفوف الموضوعية الشخصية: أبعاد التصنيف، فصل المتابعة عن «لك»، صفحة الموضوع، منع التكرار، وبوابة التنبيه العاجل.

كما أُضيفت JT-18 للخريطة والنطاق المحلي، وJT-19 للأخبار المحلية ومصادر النشر، وJT-20 كرحلة فرعية للتغذية من الصف إلى الصفحة الموضوعية. تتوقف التفاصيل التنفيذية التابعة إذا لم تُحسم قرارات D-29/D-30/D-31.

D-15 مسألة امتثال قانوني تحتاج تحديد الأسواق والاستعانة بخبرة قانونية مؤهلة؛ هذه الوثيقة لا تقرر بذاتها انطباق قانون بعينه. وقرار منتج لا يجيز تجاوز ضوابط الأمن أو القيود الرسمية للتقنية.

## 7. القياس: شجرة نتائج لا لوحة أرقام للزينة

### مؤشر النتيجة الأولي

**نسبة الجلسات التي يصل فيها المستخدم إلى منفعة محلية موثوقة أو حالة نهائية صادقة.** لا يعتمد إطلاقه كرقم وحيد قبل تعريف الجلسة والنافذة ومعيار «المنفعة» واختباره ميدانيًا.

### مؤشرات لكل رحلة

| الرحلة | مؤشر نتيجة مقترح | حواجز لا يجوز تدهورها |
|---|---|---|
| JT-01 أول استخدام | الوصول إلى أول منفعة/متابعة مفيدة | جمع بيانات أقل، عدم إكراه التوثيق أو الإشعارات |
| JT-02 التغذية | فتح عنصر مؤهل/تفاعل مفيد | التكرار والتسريب والتوسع الجغرافي الصامت |
| JT-03 السؤال/الطلب | سؤال يصل لحل/حالة نهائية قابلة للفهم | ازدواج النشر، الطلبات التي تبقى مفتوحة بلا تفسير |
| JT-04 البحث/Ask | استعلام يصل لنتيجة مفيدة أو توضيح مناسب | إجابة بلا مصدر، تسريب عبر AI، الإخفاق عند تعطله |
| JT-05/17 الأعمال والخدمة | ملف مناسب يؤدي إلى قناة تواصل مدعومة | شارات ثقة زائفة، سجلات مكررة، معاملات متوهمة |
| JT-10 الرسمي | رسالة مؤهلة وصلت إلى النطاق المقصود | عاجل بلا تفويض، رسالة مسحوبة ظاهرة |
| JT-11 التواصل | إشعار يقود إلى هدف صالح | تكرار التسليم، تسريب رسالة خاصة |
| JT-12/13 الثقة والسلامة | قرار توثيق/بلاغ ضمن السياسة المعلنة | كشف المبلّغ، قرار بلا تدقيق/استئناف مطلوب |
| JT-16 المعرفة المحلية | معلومة ذات مصدر وحداثة واضحة وتصحيح يصل إلى البحث | معلومة قديمة معروضة حالية، بيانات خاصة |
| JT-17 التوصية إلى خدمة | انتقال من توصية إلى سجل أصلي ثم قناة تواصل مدعومة | سجل مكرر، توثيق/معاملة موهومة، تفضيل مدفوع مخفي |
| JT-18 الخريطة والنطاق | علامة مؤهلة تفتح سجلها الأصلي ضمن النطاق المختار | محتوى خاص/مسحوب على الخريطة، توسع نطاق صامت، موقع أدق من السياسة |
| JT-19 الأخبار المحلية | خبر ذو مصدر/تاريخ ورابط أصلي يمكن فتحه، وتصحيحه ينعكس | ناشر موثوق زائف، إعادة نشر بلا حق لازم، مادة مسحوبة تظهر حالية |
| JT-20 الاكتشاف الموضوعي | انتقال من صف مؤهل إلى صفحة موضوعية/مرشحات ثم سجل أصلي بلا نسخ | تصنيف مختلط، صفوف فارغة، تكرار مزعج، توصية غير مسندة أو تنبيه مدفون |
| JT-14 الإدارة | إعداد صالح ينفذ أثرًا قابلًا للتراجع | إعداد يغير الصلاحيات أو يكسر العميل |

لا تُقاس «النقرة» باعتبارها ثقة أو معاملة ناجحة. لا يدخل البلاغ كإشارة تفضيل. تُحدد أغراض التحليلات والاحتفاظ والوصول قبل جمع الأحداث؛ لا يُجمع نص أو مستند حساس لمجرد سهولة جمعه.

## 8. بوابة اعتماد المتطلب قبل البرمجة (Definition of Ready)

لا تدخل الشريحة التنفيذ عندما تكون أي من النقاط التالية مجهولة أو متعارضة:
- الرحلة والهدف والمستخدم والنطاق خارج/داخل محددون.
- IDs صحيحة وفريدة: JT واحد أو أكثر، ومعايير AC، ومعرّفات UJ من السجل الموحد.
- مصدر الحقيقة والمالك والسطوح الإسقاطية/أحداث الإبطال واضحون.
- الصلاحيات والخصوصية والنطاق الجغرافي وحالات السجل والفشل موثقة.
- مخطط UI/UX يغطي الحالات الفارغة والخطأ وعدم الأهلية وRTL والوصولية.
- عقد API ومصدره معروفان: في هذا المستودع يُولد وصف OpenAPI من الكود عبر springdoc، ولا تدار نسخة YAML يدوية موازية؛ توليد العميل وفحص التوافق موثقان في CI.
- fit-gap والترحيلات والتبعيات والقرار D محسومة أو ممنوع الجزء التابع حتى تُحسم.
- AC قابلة للتكرار، ولها أسلوب اختبار ومسؤول وبيئة مطلوبة.
- مؤشرات النجاح وحواجز السلامة محددة، ولا أهداف بلا أساس.

## 9. بوابة قبول الشريحة (Definition of Done)

- كل AC متأثرة مرتبطة باختبارات ناجحة على commit محدد أو موثقة «غير مثبتة» بسبب معلوم.
- اختبارات وحدة/تكامل/عقد/واجهة مناسبة؛ الرحلة لا تسمى E2E إذا توقفت عند REST.
- الكود والوثائق والعقد المولّد والعميل المولّد (حيث ينطبق) متزامنة؛ لا ملفات مولدة تُعدّل يدويًا.
- الملكية والصلاحيات والجغرافيا والخصوصية والتكرار والحالات المنتهية مختبرة.
- مراجعة RTL والوصولية على الشاشات المستهدفة، مع إثبات يدوي عند الحاجة.
- القياسات لا تسجل معلومات حساسة بلا غرض ولا تحتسب التحميل نجاحًا.
- مراجعة بشرية للـPR، وفحوص أمن وCI خضراء على الرأس نفسه. نجاح الفحص ليس تفويض دمج.
- قرار المالك الصريح مطلوب لأي دمج أو إطلاق محجوز له. لا تدمج أي خطة متسلسلة خارج ترتيبها.

| مرحلة الخطة الموحدة | النتيجة التي ينبغي إثباتها | مالك المسار |
|---|---|---|
| 0 | خط أساس حي، اعتماديات/ترحيلات/فروع واضحة، أسرار آمنة، بوابة بناء قابلة للتكرار | Backend + Release owner |
| 1 | هوية وصلاحيات ووقائع ثقة منفصلة قابلة للاختبار | Backend + Product |
| 2 | مصدر حقيقة وعقود واكتشاف قابل للربط بلا تكرار | Backend + Product |
| 3 | تغذية نافعة ذات نطاق ومرئية وانطباعات معرفة | Backend + UX/Mobile |
| 4 | رسالة رسمية بمصدر وتفويض وسريان وتصحيح/سحب | Backend + Product/Safety |

| 7 | إشعارات ومحادثات قابلة للاسترداد ولا تكرر الأحداث | Backend + Mobile |

موجات C-0..C-11 في خطة الباك-إند وموجات M-0..M-8 في خطة الجوال هي أدوات تسليم مرتبطة بهذه المراحل، وليست خارطة موازية مستقلة. إذا تعارضتا مع مصدر الخطة أو تبعية متحققة، تُحدّث الوثائق في PR واحد متسق.

## 11. عقد العمل بين التخصصات

### مدير المنتج → UI/UX
المشكلة، الجمهور، JT/AC، القيود، المحتوى والمصطلحات، حالات الفشل، الدليل والقياس. لا يرسل رسمًا كحل مفروض قبل استكشاف الحاجة.

### UI/UX → Backend
الحالات والبيانات التي ينبغي للمستخدم فهمها، الصلاحيات الظاهرة، حالات السريان/القدم، النطاق، رسائل الخطأ، وأثر تغيير الحالة. لا يفترض المصمم وجود حقل أو صلاحية لمجرد احتياج الشاشة.

### Backend → Mobile
عقد HTTP موثق، حالات الخطأ، قواعد الصلاحية والحالة، pagination والتكرار، نسخة عقد OpenAPI مولدة ومعروفة. لا يعتمد الجوال على أسماء موارد افتراضية في جدول UX.

### Mobile → Product/UX
دلائل التفاعل الفعلية واختبارات golden/RTL/الوصولية والتكامل، الأداء والحالات غير المغطاة. لا يعد الجوال بأن العملية نجحت قبل استجابة المصدر المالك.

### الجميع → قرار الإطلاق
تقرير قبول الرحلة بصيغة §30.1 من مواصفة الرحلات، السجلات المقيسة، مخاطر الباقية وخطة التراجع. قرار المنتج يثبت المنفعة، والاختبار يثبت السلوك، والمالك يقرر الدمج/الإطلاق.
