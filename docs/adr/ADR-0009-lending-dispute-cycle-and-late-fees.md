# ADR-0009: the loan's dispute cycle and the late-fee rules — the ADR-0004 deferrals close through the shared events and the owner's frozen terms (Plan D-09 closure)

- **Status:** Accepted (owner-ordered execution — the two deferrals ADR-0004 documented as owned-and-temporary are opened per the owner's standing order, governed by the official documentation exclusively)
- **Governing references (official documentation exclusively):**
  - Spring Modulith reference — Events (`@ApplicationModuleListener`, AFTER_COMMIT/REQUIRES_NEW — the freeze/resolution writes ride their own transactions; a consumer failure never rolls the dispute row back) and the module-boundary discipline (no module imports a sibling; cross-module interaction is events or shared contracts)
  - Spring Data JPA reference — derived queries, state-guarded idempotent writes
  - PostgreSQL documentation — `EXCLUDE` constraint rebuild (a same-migration DROP/ADD pair; no VALIDATE semantics apply to exclusion constraints), `CHECK … NOT VALID` + separate `VALIDATE` (the access-lock discipline), `btree_gist` (the V41/V174 house precedent)
  - The parallel contracts ledger's own rule — "at the first cross-boundary consumer the record moves to `shared/api`, by documented decision not improvisation" (the B-08/`MessageReceivedEvent` precedent)
  - Stripe payment lifecycle via the EXISTING payments engine — the ONE refund contract, never reimplemented

## The decisions

1. **The dispute subject generalizes (the `DisputeOpenPort` seam materializes).** ADR-0004 named the mechanism: "generalizing its subject is a dedicated contract change". The contract change lands as the module-contract PAIR the booking path has used since V20: the dispute events move to `shared/api` carrying their subject (`DisputeOpenedEvent`/`DisputeResolvedEvent` gain `DisputeSubject subjectType` + the nullable `bookingId`/`loanId` pair — exactly one is set, the V177 pairing CHECK is the row-level twin), and the disputes module gates on the new `LoanPartyProvider` shared contract (the `BookingParticipantProvider` twin, implemented by the lending module's `LoanPartyProviderAdapter`). No module imports a sibling; no second dispute engine exists anywhere.
2. **The freeze is real and holds the period.** `Loan.markDisputed()` — dead code since ADR-0004 — gains its only writer: the lending module's `LoanDisputeListener`, consuming the shared `DisputeOpenedEvent` (LOAN subject) and entering DISPUTED from ACTIVE (the ADR-0004 gate verbatim, state-guarded idempotent). The freeze also holds the PERIOD: `DISPUTED` joins the live set in `isLive()`, the overlap query, and the V177 EXCLUDE rebuild — the item is with the borrower, so an overlapping request during the dispute is refused exactly as for the other live states.
3. **The resolution branches on the machine's edges, the money never moves in disputes for loans.** `DisputeResolvedEvent` (LOAN subject) drives the same listener: a `REFUND_CONSUMER` decision TERMINATES the loan through the new `cancelFromDispute` edge (DISPUTED → CANCELLED — the only controlled path an ACTIVE loan has ever had to cancellation), whose `LoanCancelledEvent` drives the payments module's own listener (`autoRefundByLoan`) and the ledger's mirror — the ONE refund contract; disputes records no refund and calls no refund port for loans. Any other decision releases the freeze through `resumeFromDispute` (DISPUTED → ACTIVE — the exact inverse of the only entry edge) and publishes `LoanDisputeResolvedEvent`. `LoanDisputedEvent`/`LoanDisputeResolvedEvent` join `shared/api`; the notifications module writes both parties' receipts (`LOAN_DISPUTED`/`LOAN_DISPUTE_RESOLVED`) — the event ADR-0004's javadoc promised ("the loan-side state and the event exist now") is true in code now, not prose.
4. **The REST surface is the booking twin.** `POST /api/v1/loans/{loanId}/disputes` (201 — RFC 9110 §15.3.2, a NEW path so the baseline gains it additively, no gate entry) and `GET /api/v1/loans/{loanId}/disputes` (the party-or-ADMIN gate) live in the disputes module's own controller — the booking endpoints stay byte-identical. `DisputeResponse` gains `subjectType`/`loanId` additively.
5. **The late-fee rules open through the owner's own frozen terms.** The offer gains the owner's optional per-day late surcharge (`late_fee_per_day_minor`, zero = none — the wire accepts it as an OPTIONAL field, omitted = 0, no client break); the loan FREEZES its copy at request time (the ADR-0002/0004 amount-source lesson: never caller-supplied, frozen before any computation); the settlement (`close`) derives the lateness from the stamped `returned_at` against the period's end — whole days, a partial day rents the whole day (the offer's own `feeFor` ceiling semantics verbatim) — and records `late_days`/`late_fee_minor` on the Envers-audited loan row. The collection rides the documented follow-up settlement leg (the deposit's leg — ADR-0004 decision 1), not silently modeled: one intent per loan stands (the V174 UNIQUE), no second payment engine, no fee charged implicitly.
6. **The A-03 arrears close in the same stroke.** `LoanClosedEvent` — published since ADR-0004 with NO listener ("no event without a listener" is ADR-0004's own discipline) — gains the notifications listener (`LOAN_CLOSED`, both parties' terminal receipt). The DB-side membership guard catches up with the Java enum: the V180 widening carries the twenty-two values the `NotificationType` enum names — including the three decision-gate types ADR-0004 added without widening the CHECK (the measured stage-8 gap: a preference row for any of them violated the surviving V164 guard at flush time — the exact defect class V110's header documents).
7. **Schema discipline.** V177 (the subject columns + the pairing/subject CHECKs NOT VALID + the EXCLUDE rebuild), V178 (VALIDATE), V179 (the late-fee terms), V180 (the CHECK widening NOT VALID), V181 (VALIDATE) — every column additive, every constraint in the house's NOT VALID/VALIDATE split, every Envers mirror in the V38/V172 pattern, no applied migration touched.

## Consequences

- The dispute cycle is end-to-end: open (any party) → freeze (the machine + the period) → resolve (the release or the refund-cancel through the ONE refund contract) → receipts (both parties, every leg).
- The lending machine's edges are paired: every entry has its exit, every event has its listener, every transition is guarded, stamped, audited.
- The notifications' type guard matches the Java enum for the first time since stage 8 — the preference surface is honest for all twenty-two types.
- The late-fee terms are the owner's own words, frozen, computed, and audited — a caller can no more buy a smaller late fee than a smaller fee.
