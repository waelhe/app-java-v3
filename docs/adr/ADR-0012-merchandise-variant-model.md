# ADR-0012: the merchandise model gains purchasable variants — the ADR-0002 variant deferral opens (Saleor plan Phase 2)

- **Status:** Accepted (owner-ordered execution — the owner's standing directive resolves every external gate by the global practice of the official documentation; governed by the official documentation exclusively)
- **Governing references (official documentation exclusively):**
  - [Saleor — Product Overview](https://docs.saleor.io/developer/products/overview) — product vs. variant, SKU, price/stock ownership at the variant, categories vs. collections
  - [Saleor — Channels](https://docs.saleor.io/developer/channels/overview) — what a sales context is and when it earns its own dimensions
  - [Saleor — product models](https://github.com/saleor/saleor/blob/main/saleor/product/models.py) — the variant's field shape as the functional benchmark
  - The merged Phase 2 plan — [the Saleor fit-gap study](../research/saleor-commerce-backend-fit-gap.md) §7 Phase 2 (items 1–4), PR #602

  - The existing contracts — `Product`/`ProductRepository`/`ProductInventoryService` patterns REUSED verbatim for the variant, never reimplemented

## The decision

This ADR opens ADR-0002's recorded variant deferral («Variants remain out of scope — recorded as deferred capability, not a gap») exactly as ADR-0010 opened that same document's mixed-seller deferral: by deciding the four Phase 2 specification items against the official documentation, then implementing against the decisions.

1. **Product identity is not a variant (the Saleor separation, adopted).** `Product` stays the descriptive identity — title, description, category, provider, lifecycle. A new `ProductVariant` (same `marketplace-catalog` module, its owning boundary) is the purchasable unit when a product genuinely sells as options: its own SKU, its own authoritative price/currency, its own stock and reserved counters, its own availability lifecycle. The catalog module remains the owner — no new module, no second engine (the study's hard rule). The variant's option values ride a free-form display name (e.g. «Large / Red») in this slice — the option vocabulary an attribute-typed system would carry is deliberately NOT built ahead of a real taxonomy requirement (the category-attribute dictionary stays the classification surface, decision 8); the store category plus its attribute dictionary remains the product-type-classification equivalent, exactly as the study measured it («Partial — not a full product-type/variant-option/SKU system»), and this ADR closes the variant half of that sentence without speculating the attribute half.

2. **The zero-variant product is untouched.** A product with no variants keeps selling exactly as today — the product-level price and stock stay the authoritative record the cart snapshots (ADR-0002's boundary verbatim). Variants are strictly additive: a seller who never registers a variant observes zero change. Saleor materializes this as an implicit default variant; this platform keeps the existing single-level path as the zero-variant case — behavior-identical for every existing product, no migration of live rows, no fake variant invented for a unique item.

3. **SKU uniqueness is per provider (the seller's namespace).** The database pins `UNIQUE (provider_id, sku)`. Two sellers may both use `RED-XL` — each owns their SKU space — but one seller's namespace is unique forever (a soft-deleted variant keeps its SKU reserved, the V70 identity stance). The `provider_id` column is denormalized from the owning product at the variant's creation, inside the same module and transaction (the V184 `orders.seller_id` precedent), because a cross-table unique constraint is not expressible — the denormalization is write-path-maintained, never client-supplied.

4. **Price and stock ownership follows the variant when variants exist.** When a product carries variants, each variant's price is the authoritative unit price and each variant's stock is the shelf the reservation arithmetic rides — the same conditional-UPDATE mechanism, mirrored onto the variant (`ProductRepository.reserve/release/commit` shapes verbatim on `ProductVariantRepository`). The cart/checkout integration that consumes this (the orders-side slice) lands as its own PR referencing this ADR; until it lands, the variant surface is the seller's own write/read path only — no consumer is changed in this slice.

5. **Channels are deferred — the single sales context stands (Phase 2 item 3, decided).** Saleor's channel is a coherent business context that can change publication, pricing, availability, tax and promotion eligibility per sales surface. This platform operates exactly one sales context today (the platform storefront) and its geography/access dimensions are already owned elsewhere (service areas, neighborhood geo). The global-practice answer is the one the study itself frames: a channel earns its own dimensions when a second real sales context exists (a B2B portal, a separate market, a mobile-only surface). Until then, per-channel anything would be speculative structure — deferred with this ADR as the recorded trigger.

6. **Category hierarchy and collections are separated and deferred (Phase 2 item 2, decided).** In Saleor, categories are the navigation taxonomy (hierarchical, one product placement) while collections are curated merchandising groups (cross-category, campaign-driven). This platform's `StoreCategory` is a flat data-managed dictionary that serves the current storefront truthfully; a hierarchy lands only when navigation depth is a real requirement (the trigger: the storefront read surface needs a drill-down the flat vocabulary cannot express), and collections land with the merchandising wave they serve. Neither is a gap today — both are recorded capabilities with named triggers.

7. **Multi-location inventory is deferred with its model defined (Phase 2 item 4, decided).** The study's own gate — add multi-location only with a defined reservation/allocation/transfer model and no-oversell proof — resolves to: the single-stock conditional update already proves no oversell for the single-location reality of this platform's sellers (V184 + the whole-map atomic reservation). The model a future multi-location wave must bring is recorded here so it is never improvised: warehouse entities owned by the catalog module, per-variant-per-warehouse stock rows, reservation as a conditional UPDATE on the specific warehouse row, allocation at fulfillment (which warehouse ships which line), transfer as a two-row guarded movement, and a concurrency test proving two placements competing for the last unit across locations cannot both win. The trigger is a real seller operating from multiple stock locations.

8. **The no-fake-variants rule survives intact (ADR-0002 verbatim).** Unique items — a particular used sofa, a particular property, an appointment — never gain variants. Variants exist only where a product genuinely sells as purchasable options (size, color, package). The category-attribute dictionary keeps serving descriptive metadata for such listings; it is not a variant system and does not become one.

## Consequences

- The seller's surface gains the variant lifecycle: register under an owned product, own read/list, set stock (absolute write, refused below the reserved set), suspend/reactivate availability, archive (terminal) — the `ProductInventoryService` ownership shape verbatim (the caller IS the product's provider, or an ADMIN; anyone else answers the honest 404).
- The migration is additive-only (V219): a new `product_variants` table with its CHECK family and its Envers mirror landing in the same migration (the V24/V33 discipline — a base table without its `_aud` twin breaks audit INSERTs silently).
- The observation pin gains the variant commands in the same PR that introduces them (the `ObservationCoverageFilesTest` discipline — commands observed, reads not).
- The OpenAPI surface is additive-only: new paths under the store namespace; no existing contract changes, no gate entry required.
- Zero Modulith boundary changes: no new module, no new SPI, no new events in this slice — the variant is born inside the catalog module and crosses no boundary until the orders-side integration PR.
- ADR-0002's deferral clause is superseded by this ADR; ADR-0002 remains the immutable record of the stage it closed, and this ADR is the documented opening of its own named deferral.
